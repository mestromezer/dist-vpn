# Тест-кейсы для проверки после деплоя

Всё в этом файле — функционал, который **реализован и покрыт юнит/интеграционными
тестами с моками**, но ни разу не проверялся против настоящей инфраструктуры (реальные
VDS, реальный браузер, реальный Ansible-контроллер). Вынесено сюда специально, чтобы не
путать "код существует и протестирован в изоляции" с "работает по-настоящему, целиком" —
второе можно подтвердить только руками, после деплоя.

Каждый кейс: предусловия → шаги → ожидаемый результат. Отмечай `[x]` по мере прохождения.

---

## 1. Полный деплой на два VDS (сквозной сценарий)

Точные команды — в истории проекта (пошаговый деплой RU entry + зарубежная exit VDS +
Platform). Кратко:

- [ ] Platform поднимается на зарубежной VDS через `docker compose`, `/docs` отдаёт Swagger
- [ ] Обе Agent-ноды (RU entry + зарубежная exit) проходят enrollment и появляются в
      `GET /nodes` со статусом `healthy` (не только `docker ps` показывает `running` —
      именно статус в реестре Platform)
- [ ] `PATCH /nodes/{id}` с `public_address` проходит для обеих нод
- [ ] `POST /cascades` собирает связку, `GET /cascades/{id}` показывает `status: up`
- [ ] `POST /users` + `GET /users/{id}/connection/{cascade_id}` отдаёт `vless://`-ссылку
- [ ] Ссылка реально импортируется в клиент (v2rayN/NekoBox/sing-box), устройство
      подключается и получает интернет через связку

## 2. Admin Client против настоящего Platform

Ни разу не запускался в браузере против живого Platform — весь UI проверен только
моками (`fetch`/`WebSocket`).

- [ ] `npm run dev` (или прод-сборка) с `VITE_API_URL`, указывающим на реальный Platform
- [ ] Логин с паролем администратора из логов Platform проходит, форсированная смена
      пароля при первом входе работает
- [ ] Список нод обновляется живьём при появлении новой ноды (WS, не поллинг)
- [ ] Граф топологии показывает связки, статус (up/degraded/down) визуально соответствует
      реальному состоянию в БД
- [ ] Новая связка, созданная в другой админ-сессии, появляется на топологии живьём через
      WS без обновления страницы (`type: "cascade"`, `event_bus.py::publish_cascade_event`
      + `applyRealtimeMessage`'s `case 'Cascade':` — реализовано и покрыто юнит-тестами
      обеих сторон, но живой WS-доставки через настоящий браузер+Platform ещё не было)
- [ ] Кнопка "Test connection" на связке реально доходит до Agent'а и показывает
      человекочитаемый результат теста
- [ ] История тест-запросов (`TestHistoryList`) отображает реальные записи и реально
      листается постранично (`page=2` и далее — не только первая страница)
- [ ] Создание пользователя, отзыв пользователя — реальный round-trip
- [ ] **Формы управления нодами** (`NodeEnroll`/`NodeEdit`/decommission, TZ-6 §3.1):
      сгенерированный enrollment-токен реально принимается провижининг-шагом Agent'а на
      чистой VDS (см. §1/§3 выше — весь end-to-end сценарий добавления новой ноды в пул
      через Admin Client, а не через ручной вызов API); `PATCH` роли/`public_address`
      через `NodeEdit` отражается в `GET /nodes/{id}`; decommission-кнопка реально
      переводит ноду в `DECOMMISSIONED` и убирает её из пула exit-кандидатов связок

## 3. Provisioning на реальном VDS/VM

Ни разу не гонялся `ansible-playbook` против настоящего Ubuntu/Debian-хоста —
только синтаксическая валидация YAML/Jinja2 в песочнице без Ansible-контроллера.

- [ ] `ansible-playbook site.yml -l entry_nodes -e role=entry --ask-vault-pass` проходит
      целиком на чистой VDS (base_hardening → docker_install → agent_install)
- [ ] SSH-хардненинг реально применяется (root-логин отключён, вход только по ключу) и
      **не обрывает текущую SSH-сессию Ansible** в процессе применения
- [ ] `docker-socket-proxy` реально стартует, Agent-контейнер реально получает доступ к
      Docker через него (не напрямую к `docker.sock`) — `docker_manager.py` успешно
      создаёт Xray-контейнер
- [ ] ufw открывает ровно задокументированные порты (443/tcp для entry, 443/tcp для
      exit) и ничего лишнего — `ufw status` после прогона
- [ ] Нода после провижининга реально доходит до Platform и появляется как `healthy` в
      `GET /nodes` (это и есть закрытие давнего TODO "верификация HEALTHY-статуса")
- [ ] Shallow git clone по закреплённому commit SHA (`agent_image_source:
      build_from_source`) реально работает против GitHub — теоретический риск
      `uploadpack.allowReachableSHA1InWant` ни разу не проверялся на практике

## 4. mTLS вживую между независимо написанными Agent и Platform

Обе стороны писались параллельно по общей спецификации, но никогда не были
протестированы друг против друга за пределами моков.

- [ ] Agent на чистой ноде проходит bootstrap-enrollment (CSR → подписанный сертификат
      от Platform CA) и устанавливает реальный mTLS-канал
- [ ] Перезапуск Agent-процесса/контейнера использует персистнутую identity (не
      повторный enrollment) — проверить по логам, что второй раз CSR не отправляется
- [ ] CA-сертификат, скопированный оператором из Platform в Agent (`agent_mtls_ca_cert_src`),
      реально проходит проверку — Agent не падает на "unknown CA"

## 5. Failover вживую

- [ ] Реально остановить Agent-процесс/контейнер на entry-ноде, дождаться
      `PLATFORM_NODE_HEARTBEAT_TIMEOUT_SECONDS` (по умолчанию 45с) — нода и её каскады
      должны перейти в `down` в `GET /nodes`/`GET /cascades` без ручного вмешательства
- [ ] `POST /cascades/{id}/migrate-users` на живой связке с реальными подключёнными
      Agent'ами — пользователи реально переносятся (RemoveUser со старой,
      AddUser на новую), проверить по `GET /users/{id}` и по факту, что старая ссылка
      перестаёт работать, а новая — работает
- [ ] Перезапуск упавшего Agent'а — статус ноды реально возвращается в `healthy` на
      следующем heartbeat (реактивное восстановление, без участия планировщика)

## 6. Лимит устройств вживую

- [ ] Подключить с одного `vless://`-URI больше устройств, чем `User.max_devices` —
      Platform должен принудительно разорвать все подключения этого пользователя на
      затронутой ноде (реальный кик, не просто запись в БД) и записать
      `UserDeviceKickEvent`
- [ ] После кика устройства реально могут переподключиться (не заблокированы навсегда)

## 7. Мониторинг ресурсов вживую

- [ ] `NodeResourceSample` реально накапливается по одной строке на каждый heartbeat
      под реальной нагрузкой в течение продолжительного времени (несколько часов) —
      подтвердить, что `provisioned_user_count`/`online_user_count`/`online_device_count`
      меняются адекватно реальному числу пользователей/подключений
- [ ] `cpu_percent`/`mem_percent`/`disk_percent` от `psutil` внутри Agent-контейнера
      отражают реальную нагрузку (не залипают на 0 или на первом замере)
