# Admin Client

Полное ТЗ: [../docs/TZ-6-admin-client.md](../docs/TZ-6-admin-client.md).

Кратко: React + TypeScript + Vite, [react-admin](https://github.com/marmelab/react-admin) как основа (минимум кастомного кода/CSS — MUI из коробки), [React Flow](https://reactflow.dev/) для графа топологии каскадов. Данные — по контракту [`../contracts/rest/openapi.yaml`](../contracts/rest/openapi.yaml).

Этот README описывает состояние после **третьего среза** (ветка `admin-client/scaffold`): к второму срезу (граф топологии, ресурс `cascades`, UI тест-запроса, принудительная смена пароля, `users`) добавлены live-push через `WS /events` (граф топологии и результат тест-запроса теперь обновляются в реальном времени, с автоматическим откатом на поллинг, если сокет недоступен) и история тест-запросов по каскаду (`GET /cascades/{id}/tests`, `TestHistoryList`). Полный список того, что сознательно НЕ входит в этот срез — см. "Scope этого среза / TODO" ниже. Первый и второй срезы описаны в истории коммитов этого файла (`git log -- admin-client/README.md`).

## Установка

Требуется Node.js ≥ 20 (проверено на Node 22) и npm.

```bash
cd admin-client
npm install
```

## Переменные окружения

Единственная переменная — адрес Platform REST API (см. `contracts/rest/openapi.yaml`, `servers: /api/v1`):

```
VITE_API_URL=http://localhost:8000/api/v1
```

По умолчанию (если переменная не задана) используется то же значение — `http://localhost:8000/api/v1`. Скопируйте `.env.example` в `.env.local` и поменяйте адрес при необходимости:

```bash
cp .env.example .env.local
```

`.env.local`/`.env` не коммитятся (см. корневой `.gitignore`). Важно: **всё, что попадает в `VITE_*`, оказывается в собранном клиентском бандле в открытом виде** — сюда нельзя класть ничего, кроме публичного адреса API (см. TZ-6 §5).

## Запуск в разработке

```bash
npm run dev
```

Поднимает Vite dev-server (по умолчанию `http://localhost:5173`) с hot-reload. Без поднятого Platform API (`VITE_API_URL` недоступен) логин не пройдёт — экран логина отрисуется, но `POST /auth/login` будет возвращать сетевую ошибку/таймаут. Platform как таковой уже во многом реализован (ветка `platform/api-skeleton` в соседнем воркчту `dist-vpn-platform`, см. его README), но ещё не влит в `main` и не является частью этого репозитория/среза — по умолчанию просто нечему отвечать на `localhost:8000`, если её не поднять отдельно (`docker compose up` в `platform/`).

- `src/resources/TestRequestButton.test.tsx` — кнопка "Test connection": старт теста (`POST /cascades/{id}/test`), поллинг `GET /tests/{id}` пока результат не готов, рендер понятного текста по каждому исходу (не `"outcome"` в JSON); плюс WS-сценарии — результат приходит live-пушем `LinkTest` без единого вызова `GET /tests/{id}`, чужой (несовпадающий) `test_id` игнорируется, при разрыве сокета — откат на REST-поллинг.
- `src/resources/TestHistoryList.test.tsx` — история тест-запросов (`GET /cascades/{id}/tests`): рендер прошлых попыток с человекочитаемым исходом, пустое состояние, предупреждение (не краш) при ошибке запроса, и реальная постраничная навигация (клик "next page" реально дёргает `page=2`, а не режет на клиенте один большой заранее загруженный массив).
- `src/auth/PasswordChangeGuard.test.tsx` — сквозной (в рамках jsdom) тест: логин с `must_change_password: true` в ответе принудительно показывает экран смены пароля вместо обычного постлогинового маршрута.

Важная деталь для тестов графа: `reactflow` в jsdom не работает "из коробки" — jsdom не реализует `ResizeObserver`, `DOMMatrixReadOnly`, ненулевые `offsetWidth`/`offsetHeight`/`getBoundingClientRect()`, и `getBBox()` на SVG-элементах (и последний нужно патчить именно на `SVGElement.prototype`, а не `SVGGraphicsElement.prototype` — jsdom не вставляет `SVGGraphicsElement` в реальную цепочку прототипов создаваемых SVG-элементов, хотя сам конструктор как глобал существует). Без этих стабов `reactflow` либо синхронно бросает исключение при монтировании подписанного ребра (и React Router's error boundary съедает всю страницу), либо ноды/рёбра остаются `visibility: hidden`/неизмеренными. Все стабы — в `src/setupTests.ts`, с комментариями, почему каждый нужен.

## Что реализовано в этом срезе

- **Стек**: Vite + React 19 + TypeScript, `react-admin` 5.x (MUI из коробки), `reactflow` 11.x — все зависимости, указанные в ТЗ-6 §2.
- **`<Resource name="nodes">`** (`src/resources/nodes.tsx`) — список и просмотр по схеме `Node` из контракта (id, label, role, region, status, agent_version, last_heartbeat_at). Фильтры по `role`/`status` (единственные, что поддерживает `GET /nodes` по контракту), пагинация, сортировка колонок — всё штатное поведение `<List>`/`<Datagrid>` react-admin, без единой строчки кастомного CSS. Статус ноды отображается цветным MUI `<Chip>` (зелёный/жёлтый/красный/серый/синий) — человекочитаемо, не голый enum-текст (TZ-6 §6).
- **`<Resource name="cascades">`** (`src/resources/cascades.tsx`) — список и просмотр по схеме `Cascade` (id, entry-нода, пул exit-нод, статус, hop A presets). Тот же паттерн цветного `<Chip>` для `Cascade.status`, что и у `nodes`. Просмотр включает кнопку тест-запроса (см. ниже).
- **Реальный граф топологии каскадов** (`src/topology/TopologyPage.tsx`, `src/topology/graph.ts`, маршрут `/topology`) — заменяет заглушку первого среза. Ноды (`GET /nodes`) размещены в две колонки по роли (entry слева, exit справа), рёбра — по одному на пару (`Cascade.entry_node_id`, `exit_node_id`) из `GET /cascades`. Цвет рамки ноды и цвет/штрих/анимация/подпись ребра кодируют статус (`healthy`/`degraded`/`down`/…) — прямое выполнение TZ-6 §3.1 ("где обрывается соединение… понятным человеку"): для `down`-каскада ребро — анимированное, красное, пунктирное, с подписью "Down — connection breaks here", видно без наведения.
- **Live-push через `WS /events`, с откатом на поллинг** (`src/realtime/eventsSocket.ts`, `src/realtime/useEventsSocket.ts`, `src/topology/liveTopology.ts`) — этим срезом граф топологии и результат тест-запроса (см. ниже) переведены с чистого поллинга на `WS /events`, реализующее TZ-6 §2/§4 и TZ-5 §4.3/§7 ("push, не только по запросу"):
  - `eventsSocket.ts` — фреймворк-независимый клиент сокета: экспоненциальный backoff (старт 1с, кап 30с — те же дефолты, что и у переподключения control-plane Agent'а), окно "стабильности" (`stableAfterMs`, 2с — соединение, которое открылось и тут же закрылось, не путается с рабочим), и статус `unavailable` после `failuresBeforeUnavailable` (3) подряд неудачных попыток — именно в этот момент клиент откатывается на поллинг. Токен передаётся query-параметром `token` (не заголовком — браузерный `WebSocket` не может ставить `Authorization` на handshake), имя параметра подтверждено чтением обработчика на стороне Platform (`platform/src/dist_vpn_platform/api/routes/events.py` в соседнем воркчту).
  - `liveTopology.ts` (`useLiveTopologySnapshot`) — всегда поллит, пока сокет не станет `open` (гарантирует первый полный снимок через REST независимо от скорости подключения сокета), затем ставит поллинг на паузу и применяет входящие сообщения (`applyRealtimeMessage`) поверх последнего снимка; при разрыве сокета поллинг возобновляется автоматически. `TopologyPage.tsx` показывает текущий транспорт чипом ("Live (WebSocket)" / "Polling"), чтобы не гадать, что на самом деле обновляет граф.
  - Формат сообщений сверен с реальным исходником Platform в соседнем воркчту (`platform/src/dist_vpn_platform/services/event_bus.py`, ветка `platform/api-skeleton`): Platform шлёт `{"type": "health_event"|"cascade"|"link_test", "data": {...}}` — **snake_case-теги**, не `HealthEvent`/`Cascade`/`LinkTest`, как можно было бы предположить из прозы контракта; `parseRealtimeMessage` принимает оба варианта. **Обновление этого среза**: Platform теперь шлёт и полноценный `type: "cascade"` (`event_bus.py::publish_cascade_event`, вызывается при создании каскада, при авто-детекте DOWN по таймауту хартбита (`health_scheduler.py`) и при восстановлении каскада на очередном хартбите) — `applyRealtimeMessage`'s `case 'Cascade':` был реализован заранее, "на вырост", ещё когда этого сообщения не существовало, и теперь просто заработал без изменений в коде; понадобилась только правка doc-комментариев (см. `eventsSocket.ts`/`liveTopology.ts`). Смена статуса уже известного каскада по-прежнему дублируется и через `health_event` с `cascade_id`/без `node_id` — оба сообщения бьют по одному и тому же переходу, `applyRealtimeMessage` обрабатывает оба.
  - **Статус проверки**: код сверен построчно с реальным исходником Platform (`platform/api/routes/events.py`, `services/event_bus.py`, `services/link_tests.py`) в соседнем воркчту — это не то же самое, что сквозной прогон через настоящий браузер против поднятого Platform, такого прогона в этом срезе не было. См. "Ручная проверка" и TODO ниже.
- **Человекочитаемый UI тест-запроса** (`src/resources/TestRequestButton.tsx`, `src/resources/testOutcome.ts`, кнопка на `CascadeShow`) — по TZ-6 §3.2: `POST /cascades/{id}/test` → результат — либо live-пуш `LinkTest` через `WS /events` (пока сокет `open`), либо поллинг `GET /tests/{test_id}` (интервал 1.5с, таймаут 30с) как откат — → результат рендерится как понятное предложение через `describeTestOutcome`, а не голый JSON/enum. Каждое значение `TestOutcome` (`success`/`container_start_failed`/`tls_handshake_failed`/`proxy_no_response`/`timeout`) имеет отдельную формулировку; при `success` добавляется латентность, при наличии `detail` от сервера — он добавляется как доп. контекст, а не подменяет собственный текст клиента. `POST /cascades/{id}/test` и `GET /tests/{id}` реализованы по-настоящему (не заглушка) на ветке Platform `platform/api-skeleton` — но сквозной прогон через настоящий браузер против поднятого Platform в этом срезе не проводился, только чтение исходника и мок-`fetch`-тесты клиента. ## Аутентификация и хранение токенов

Реализовано согласно TZ-6 §5 и TZ-5 §6.3 ("localStorage запрещено для долгоживущих токенов; окончательная схема — на этапе реализации").

**Выбранная схема: и access-, и refresh-токен хранятся только в памяти** — в замыкании модуля `src/auth/tokenStore.ts` (обычная переменная JS), никогда не пишутся в `localStorage`, `sessionStorage` или в cookie, доступную JS.

Почему именно так, а не access-в-памяти + refresh-в-cookie:

1. Контракт (`POST /auth/refresh`) принимает `refresh_token` как **поле JSON-тела запроса**, а не как cookie, которую браузер прикладывает сам — то есть контракт уже предполагает, что клиент явно держит и посылает refresh-токен сам, а не полагается на httpOnly cookie.
2. Схема с httpOnly cookie для refresh-токена — решение, которое реально принимает Platform (TZ-5 §6.3 явно оставляет это "на этапе реализации"), а Platform ещё не реализован. Не хотелось фиксировать в Admin Client архитектурное решение за другую программу.
3. Полностью закрывает именно тот риск, который называет ТЗ: кража токена через XSS из постоянного хранилища. Хранилища с JS-доступом (включая `sessionStorage`) для этого не годятся — если XSS может исполнить произвольный JS, он может прочитать что угодно, что доступно из JS, а замыкание модуля (без глобальной ссылки на объект-хранилище) минимум не даёт токену пережить сам процесс/вкладку и не оставляет его в DevTools storage-инспекторе.

Цена решения: **при полной перезагрузке страницы (F5, закрытие вкладки и т.д.) сессия теряется** — оба токена обнуляются, нужен повторный логин. Это осознанный компромисс: для admin-панели с относительно нечастыми полными перезагрузками цена ниже, чем цена лишнего класса уязвимостей "долгоживущий токен, читаемый из JS". Если Platform в будущем выберет httpOnly-cookie для refresh-токена — это меняется без переделки access-токена (он и там, и там остаётся в памяти).

Технически (`src/auth/httpClient.ts`):
- `authorizedFetchJson` перед каждым запросом проверяет, не истёк ли access-токен (`expires_in` из `TokenPair`, с запасом 10 сек), и если истёк — сначала обновляет его через `/auth/refresh`.
- При ответе `401` — одна попытка форс-рефреша и повторного запроса (страховка от рассинхронизации часов/гонок).
- Параллельные рефреши схлопываются в один in-flight промис (`refreshPromise`), чтобы не насиловать `/auth/refresh` при нескольких одновременных запросах.
- `authProvider.checkError` на `401`/`403` чистит токены и просит react-admin разлогинить пользователя.

## Почему кастомный `dataProvider`, а не `ra-data-simple-rest`

`ra-data-simple-rest` ожидает список записей как **голый JSON-массив**, а общее число — в HTTP-заголовке (`Content-Range`/аналог). Контракт же возвращает конверт `{ items: [...], total: N }` (см. `GET /nodes` в `openapi.yaml`) и постраничность через query-параметры `page`/`page_size`, а не через заголовки диапазона. Городить это через кастомный `httpClient`-хук поверх `ra-data-simple-rest` показалось не проще, чем написать ~120 строк прямого адаптера (`src/dataProvider.ts`) — он и читается прямолинейнее, и явно показывает, какие ресурсы реально протестированы (см. выше).

## Замечания к контракту

Оба замечания первого среза (`GET /cascades`/`GET /users` без `total`, неясность тела `POST /auth/logout`) **уже устранены выше по цепочке**: ветка `admin-client/scaffold` подтянула из `main` коммиты `2bac197` и `d3055d7`, которые унифицировали конверт списков (`total` теперь есть у `/nodes`, `/cascades`, `/users`) и уточнили `/auth/logout` (`refresh_token` — опциональное, но рекомендуемое поле тела запроса). Слить `main` в эту ветку было безопасно и сделано в рамках этого среза: `admin-client/` эти коммиты не трогают (только `contracts/`), конфликтов не было.

Важно для следующего, кто будет смотреть на эту ветку: если `src/contract/types.ts` когда-нибудь снова разойдётся с `../contracts/rest/openapi.yaml`, **не делайте вывод "контракт не менялся" по `git log -- contracts/...` только в этой ветке** — сверяйтесь с `git log main -- contracts/rest/openapi.yaml`, эта ветка могла снова отстать от `main`. Именно так ошибся один из параллельных треков в этом раунде.

Новых замечаний к контракту в этом срезе не возникло: формы `/cascades/{id}/test`, `/tests/{id}`, `/auth/change-password`, `TokenPair.must_change_password` вполне однозначны, реализация клиента следует им буквально. `GET /cascades/{cascade_id}/tests` подтянут из `main` (коммит `f45e2c5`, см. историю тест-запросов выше) — тоже вполне однозначная форма.

**Отдельное замечание про доверие к утверждениям о "проверено вживую"**: предыдущая (прерванная сессионным лимитом) попытка этого среза оставила в нескольких doc-комментариях (`eventsSocket.ts`, `TestRequestButton.tsx`, `TestHistoryList.tsx`) конкретные, но неверные утверждения о состоянии Platform — например, что `/events` — заглушка, шлющая одно сообщение `not_implemented` и закрывающаяся, или что `POST /cascades/{id}/test`/`GET /tests/{id}`/`GET /cascades/{id}/tests` всё ещё `501`/не существуют. На момент ревизии этого среза ни одно из этого не подтверждается реальным исходником соседнего воркчту `dist-vpn-platform` (ветка `platform/api-skeleton`): `/events` — рабочий in-process pub/sub broadcaster (`services/event_bus.py`), а все три упомянутых REST-эндпойнта реализованы по-настоящему. Все такие утверждения в коде исправлены на месте (см. историю коммитов этого среза) — сверено прямым чтением исходника Platform, а не переписано на слово. Это не то же самое, что сквозной прогон через настоящий браузер против поднятого Platform — такого прогона в этом срезе так и не было, см. "Ручная проверка" ниже. Урок для следующего среза: doc-комментарии вида "verified live"/"confirmed against a running container" должны быть перепроверяемы (ссылка на конкретный файл/коммит соседнего трека), а не приниматься на веру только потому, что звучат уверенно.

## Scope этого среза / TODO

Реализовано в этом срезе (см. "Что реализовано" выше): live-push через `WS /events` для графа топологии и результата тест-запроса (с откатом на поллинг), история тест-запросов по каскаду (`TestHistoryList`, `GET /cascades/{id}/tests`).

**Сквозная проверка против настоящего живого Platform — самое важное, что осталось не сделано, и приоритет №1 для следующего среза.** Всё в этом срезе, что касается `WS /events` и связанных с ним REST-эндпойнтов, проверено (а) юнит/интеграционными тестами с мок-`fetch`/мок-`WebSocket`, и (б) прямым построчным чтением реального (не заглушечного) исходника Platform в соседнем воркчту `dist-vpn-platform` (ветка `platform/api-skeleton`, ещё не влита в `main`). Это заметно надёжнее, чем было (см. "Отдельное замечание про доверие..." выше — предыдущая попытка этого среза приняла на веру собственные неверные утверждения), но **это не сквозной прогон через настоящий браузер против поднятого Platform** — ни разу в этом срезе Admin Client не запускался в браузере против живого `docker compose up` Platform с реальным логином. В частности не подтверждено вживую:
  - что реальные `health_event`/`link_test` сообщения от запущенного Platform действительно долетают до браузера и парсятся так, как ожидает `parseRealtimeMessage` (проверено только чтением исходника + юнит-тестами на сконструированных вручную сообщениях);
  - полный цикл "нажал Test connection → живой Agent прогнал тест → LinkTest пришёл по WS → UI показал результат" — `services/link_tests.py`/dispatch к Agent'у на стороне Platform не были инсценированы против настоящего Agent'а в рамках проверки этого среза;
  - поведение при реальном обрыве сети/сервера (а не программно вызванном `triggerClose()` в тесте).

Закрыто этим срезом (было в этом списке ранее):

- **Live-обновление вновь созданного каскада при открытом WS** — Platform теперь шлёт `type: "cascade"` (`event_bus.py::publish_cascade_event`), и `applyRealtimeMessage`'s `case 'Cascade':` (реализован заранее, до появления этого сообщения) собирает новую запись `Cascade` из полного снимка, а не только патчит статус уже известного каскада. Живой браузерной проверки этого пути по-прежнему не было — см. "Сквозная проверка" выше и `TESTING.md`.
- **Многостраничная история тест-запросов** — `TestHistoryList` теперь запрашивает `GET /cascades/{id}/tests?page=N&page_size=25` заново при каждой смене страницы (`<Pagination>`), а не режет на клиенте одну заранее загруженную сотню записей. `<ListContextProvider>` получает собранный вручную (`buildListContext`) контекст вместо `useList` — `useList` пагинирует только уже полностью загруженный локальный массив и не может выразить "на сервере есть страницы, которых мы ещё не запрашивали". Проверено `TestHistoryList.test.tsx` (клик "next page" реально уходит вторым запросом с `page=2`, а не переключает уже загруженные строки); живой браузерной проверки против настоящего Platform не было.

Сознательно остаётся вне этого среза:

- **Графики потребления** (`/usage`, Recharts по ТЗ, TZ-6 §3.3) — сам эндпойнт на Platform по-прежнему `501` (перепроверено в этом срезе чтением `platform/src/dist_vpn_platform/api/routes/usage.py` — там явный `raise HTTPException(501, ...)`, ждёт telemetry-ingestion среза); UI пользователей (`<Resource name="users">`) сейчас показывает только сущность/статус/привязанные каскады, без чисел потребления. Recharts не подключён.
- **UI ротации секретов** (TZ-6 §3.4) — не реализовано, зависит от эндпойнта ротации, которого пока нет в контракте.
- **MFA/TOTP-шаг логина** — поле `totp_code` уже уходит в `POST /auth/login`, но отдельного пошагового UI (запрос кода вторым шагом) нет; будет добавлено, когда Platform реализует и включит MFA (TZ-5 §6.3).
- **Кодогенерация типов из `openapi.yaml`** — `contracts/README.md` рекомендует генерировать типизированный клиент из схемы; типы (`src/contract/types.ts`) по-прежнему переписаны вручную. Набор вырос (auth + `Node` + `Cascade` + `LinkTest` + `User`) — со следующим ресурсом стоит подключить генератор (`openapi-typescript` и т.п.), ручное сопровождение уже ощутимо более трудоёмкое, чем в первом срезе.
- **Формы для `nodes`** (добавление в пул / назначение роли / вывод из эксплуатации, TZ-6 §3.1) — вне мандата этого среза; `nodes` остаётся list/show, как в первом срезе.
- **Code-splitting сборки** — один JS-чанк (~1.18 МБ до gzip, ~370 кБ после). Не проблема при текущем размере приложения, но стоит держать в уме при добавлении новых ресурсов/графиков (усложняется дальше добавлением Recharts под графики потребления).
