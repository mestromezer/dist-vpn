# Admin Client

Полное ТЗ: [../docs/TZ-6-admin-client.md](../docs/TZ-6-admin-client.md).

Кратко: React + TypeScript + Vite, [react-admin](https://github.com/marmelab/react-admin) как основа (минимум кастомного кода/CSS — MUI из коробки), [React Flow](https://reactflow.dev/) для графа топологии каскадов. Данные — по контракту [`../contracts/rest/openapi.yaml`](../contracts/rest/openapi.yaml).

Этот README описывает состояние после **второго среза** (ветка `admin-client/scaffold`): к первому срезу (ресурс `nodes`, логин, `reactflow`-заглушка) добавлены реальный граф топологии каскадов, ресурс `cascades`, человекочитаемый UI тест-запроса, принудительная смена пароля, ресурс `users`, и починка `authProvider.logout` под обновлённый контракт. Полный список того, что сознательно НЕ входит в этот срез — см. "Scope этого среза / TODO" ниже.

## Установка

Требуется Node.js ≥ 20 (проверено на Node 22) и npm.

```bash
cd admin-client
npm install
```

## Переменные окружения

Единственная переменная — адрес Platform REST API (см. `contracts/rest/openapi.yaml`, `servers: /api/v1`):

```
VITE_API_URL=http://localhost:8000/api/v1
```

По умолчанию (если переменная не задана) используется то же значение — `http://localhost:8000/api/v1`. Скопируйте `.env.example` в `.env.local` и поменяйте адрес при необходимости:

```bash
cp .env.example .env.local
```

`.env.local`/`.env` не коммитятся (см. корневой `.gitignore`). Важно: **всё, что попадает в `VITE_*`, оказывается в собранном клиентском бандле в открытом виде** — сюда нельзя класть ничего, кроме публичного адреса API (см. TZ-6 §5).

## Запуск в разработке

```bash
npm run dev
```

Поднимает Vite dev-server (по умолчанию `http://localhost:5173`) с hot-reload. Без поднятого Platform API логин не пройдёт — экран логина отрисуется, но `POST /auth/login` будет возвращать сетевую ошибку/таймаут, что ожидаемо для этого среза (Platform ещё не реализован).

## Тесты

```bash
npm test
```

`vitest` + `@testing-library/react` + `jsdom`. На момент сдачи этого среза: 7 тестовых файлов / 20 тестов, все зелёные —

- `src/App.test.tsx` — смоук-тест: приложение рендерится и без токена в памяти показывает встроенный экран логина react-admin (поля Username/Password, кнопка Sign in).
- `src/dataProvider.test.ts` — проверяет, что `getList('nodes', …)` правильно разбирает контрактный конверт `{ items, total }` из `GET /nodes` и формирует корректные query-параметры (`page`, `page_size`).
- `src/topology/graph.test.ts` — юнит-тест чистой функции `buildTopologyGraph`: раскладка по колонкам (entry/exit), цвет ноды по `Node.status`, цвет/анимация/подпись ребра по `Cascade.status`, включая "breaks here" для `down`.
- `src/topology/TopologyPage.test.tsx` — граф реально рендерится через `reactflow` против мокнутых `GET /nodes`/`GET /cascades`: подписи нод с их статусом и подпись ребра "Down — connection breaks here" действительно оказываются в DOM (не просто в данных).
- `src/resources/testOutcome.test.ts` — юнит-тест `describeTestOutcome`: каждое значение `TestOutcome` даёт понятное предложение (не голый enum), латентность приклеивается при `success`, `detail` добавляется как доп. контекст.
- `src/resources/TestRequestButton.test.tsx` — кнопка "Test connection": старт теста (`POST /cascades/{id}/test`), поллинг `GET /tests/{id}` пока результат не готов, рендер понятного текста по каждому исходу (не `"outcome"` в JSON).
- `src/auth/PasswordChangeGuard.test.tsx` — сквозной (в рамках jsdom) тест: логин с `must_change_password: true` в ответе принудительно показывает экран смены пароля вместо обычного постлогинового маршрута.

Важная деталь для тестов графа: `reactflow` в jsdom не работает "из коробки" — jsdom не реализует `ResizeObserver`, `DOMMatrixReadOnly`, ненулевые `offsetWidth`/`offsetHeight`/`getBoundingClientRect()`, и `getBBox()` на SVG-элементах (и последний нужно патчить именно на `SVGElement.prototype`, а не `SVGGraphicsElement.prototype` — jsdom не вставляет `SVGGraphicsElement` в реальную цепочку прототипов создаваемых SVG-элементов, хотя сам конструктор как глобал существует). Без этих стабов `reactflow` либо синхронно бросает исключение при монтировании подписанного ребра (и React Router's error boundary съедает всю страницу), либо ноды/рёбра остаются `visibility: hidden`/неизмеренными. Все стабы — в `src/setupTests.ts`, с комментариями, почему каждый нужен.

## Что реализовано в этом срезе

- **Стек**: Vite + React 19 + TypeScript, `react-admin` 5.x (MUI из коробки), `reactflow` 11.x — все зависимости, указанные в ТЗ-6 §2.
- **`<Resource name="nodes">`** (`src/resources/nodes.tsx`) — список и просмотр по схеме `Node` из контракта (id, label, role, region, status, agent_version, last_heartbeat_at). Фильтры по `role`/`status` (единственные, что поддерживает `GET /nodes` по контракту), пагинация, сортировка колонок — всё штатное поведение `<List>`/`<Datagrid>` react-admin, без единой строчки кастомного CSS. Статус ноды отображается цветным MUI `<Chip>` (зелёный/жёлтый/красный/серый/синий) — человекочитаемо, не голый enum-текст (TZ-6 §6).
- **`<Resource name="cascades">`** (`src/resources/cascades.tsx`) — список и просмотр по схеме `Cascade` (id, entry-нода, пул exit-нод, статус, hop A presets). Тот же паттерн цветного `<Chip>` для `Cascade.status`, что и у `nodes`. Просмотр включает кнопку тест-запроса (см. ниже).
- **Реальный граф топологии каскадов** (`src/topology/TopologyPage.tsx`, `src/topology/graph.ts`, маршрут `/topology`) — заменяет заглушку первого среза. Ноды (`GET /nodes`) размещены в две колонки по роли (entry слева, exit справа), рёбра — по одному на пару (`Cascade.entry_node_id`, `exit_node_id`) из `GET /cascades`. Цвет рамки ноды и цвет/штрих/анимация/подпись ребра кодируют статус (`healthy`/`degraded`/`down`/…) — прямое выполнение TZ-6 §3.1 ("где обрывается соединение… понятным человеку"): для `down`-каскада ребро — анимированное, красное, пунктирное, с подписью "Down — connection breaks here", видно без наведения. Данные обновляются поллингом `GET /nodes`+`GET /cascades` каждые 5с (`src/topology/usePolling.ts`) — это осознанная временная замена WebSocket-пуша: Platform-эндпойнт `WS /events` пока не реализован (подтверждено в этом раунде треком Platform), полноценный live-push — TODO ниже.
- **Человекочитаемый UI тест-запроса** (`src/resources/TestRequestButton.tsx`, `src/resources/testOutcome.ts`, кнопка на `CascadeShow`) — по TZ-6 §3.2: `POST /cascades/{id}/test` → поллинг `GET /tests/{test_id}` (интервал 1.5с, таймаут 30с) → результат рендерится как понятное предложение через `describeTestOutcome`, а не голый JSON/enum. Каждое значение `TestOutcome` (`success`/`container_start_failed`/`tls_handshake_failed`/`proxy_no_response`/`timeout`) имеет отдельную формулировку; при `success` добавляется латентность, при наличии `detail` от сервера — он добавляется как доп. контекст, а не подменяет собственный текст клиента. **Важно**: `POST /cascades/{id}/test` и `GET /tests/{id}` на стороне Platform на момент сдачи этого среза всё ещё `501 Not Implemented` (подтверждено отчётом трека Platform в этом раунде) — UI построен строго по форме контракта (тот же подход, что и `nodes` в первом срезе, когда у Platform ещё не было реальных данных), но **сквозная проверка против живого Platform пока невозможна** — см. TODO.
- **Принудительная смена пароля** (`src/auth/ChangePasswordPage.tsx`, `src/auth/PasswordChangeGuard.tsx`) — если ответ `POST /auth/login` содержит `must_change_password: true` (новое поле контракта), `authProvider.login` сразу отдаёт `redirectTo: '/change-password'`, а `PasswordChangeGuard` (смонтирован в `CustomLayout`, видит каждую смену маршрута) принудительно возвращает туда же при любой попытке уйти на другой экран, пока флаг не сброшен. Форма вызывает новый эндпоинт `POST /auth/change-password`; при успехе флаг сбрасывается (`tokenStore.clearMustChangePassword`) и админ попадает в обычный интерфейс.
- **`authProvider.logout`** — обновлён под новый контракт: `POST /auth/logout` теперь получает тело `{ refresh_token }` (поле опционально по контракту, но явная передача — рекомендованный контрактом способ однозначно указать, какую сессию отзывать, а не полагаться на то, что сервер сопоставит её по access-токену).
- **`<Resource name="users">`** (`src/resources/users.tsx`) — список/создание/удаление(отзыв) по схеме `User`: добавить пользователя (имя + привязка к каскадам через `ReferenceArrayInput`), увидеть его каскады как чипы (`ReferenceArrayField` → `cascades`), отозвать доступ (`DeleteButton`, `DELETE /users/{id}`). Отображение потребления (`/usage`) сознательно оставлено как задокументированный TODO — эндпойнт всё ещё `501` на Platform.
- **`dataProvider`** (`src/dataProvider.ts`) — тонкая обёртка над `fetch` (не `ra-data-simple-rest`, см. обоснование ниже). `getList`/`getOne` теперь реально протестированы для всех трёх ресурсов (`nodes`, `cascades`, `users`); `create`/`delete` — для `users`.
- **`authProvider`** (`src/auth/authProvider.ts`) — `login`/`logout`/`checkAuth`/`checkError` поверх `POST /auth/login`, `/auth/refresh` (прозрачно, через `httpClient`), `POST /auth/logout`. Поддержка `totp_code` в форме логина уже прокинута в теле запроса (react-admin позволяет добавлять произвольные поля в `<LoginForm>` — сама MFA-форма/шаг это следующий срез, см. TODO).
- **Хранение токенов** — см. отдельный раздел ниже, это самое важное архитектурное решение этого стека, без изменений с первого среза.
- **Тесты**: vitest + Testing Library, 7 файлов / 20 зелёных тестов (см. раздел "Тесты" выше) — включая рендер графа топологии через реальный `reactflow` (не только на уровне данных), человекочитаемый текст на каждый `TestOutcome`, и сквозной тест на принудительный редирект при `must_change_password`.

## Аутентификация и хранение токенов

Реализовано согласно TZ-6 §5 и TZ-5 §6.3 ("localStorage запрещено для долгоживущих токенов; окончательная схема — на этапе реализации").

**Выбранная схема: и access-, и refresh-токен хранятся только в памяти** — в замыкании модуля `src/auth/tokenStore.ts` (обычная переменная JS), никогда не пишутся в `localStorage`, `sessionStorage` или в cookie, доступную JS.

Почему именно так, а не access-в-памяти + refresh-в-cookie:

1. Контракт (`POST /auth/refresh`) принимает `refresh_token` как **поле JSON-тела запроса**, а не как cookie, которую браузер прикладывает сам — то есть контракт уже предполагает, что клиент явно держит и посылает refresh-токен сам, а не полагается на httpOnly cookie.
2. Схема с httpOnly cookie для refresh-токена — решение, которое реально принимает Platform (TZ-5 §6.3 явно оставляет это "на этапе реализации"), а Platform ещё не реализован. Не хотелось фиксировать в Admin Client архитектурное решение за другую программу.
3. Полностью закрывает именно тот риск, который называет ТЗ: кража токена через XSS из постоянного хранилища. Хранилища с JS-доступом (включая `sessionStorage`) для этого не годятся — если XSS может исполнить произвольный JS, он может прочитать что угодно, что доступно из JS, а замыкание модуля (без глобальной ссылки на объект-хранилище) минимум не даёт токену пережить сам процесс/вкладку и не оставляет его в DevTools storage-инспекторе.

Цена решения: **при полной перезагрузке страницы (F5, закрытие вкладки и т.д.) сессия теряется** — оба токена обнуляются, нужен повторный логин. Это осознанный компромисс: для admin-панели с относительно нечастыми полными перезагрузками цена ниже, чем цена лишнего класса уязвимостей "долгоживущий токен, читаемый из JS". Если Platform в будущем выберет httpOnly-cookie для refresh-токена — это меняется без переделки access-токена (он и там, и там остаётся в памяти).

Технически (`src/auth/httpClient.ts`):
- `authorizedFetchJson` перед каждым запросом проверяет, не истёк ли access-токен (`expires_in` из `TokenPair`, с запасом 10 сек), и если истёк — сначала обновляет его через `/auth/refresh`.
- При ответе `401` — одна попытка форс-рефреша и повторного запроса (страховка от рассинхронизации часов/гонок).
- Параллельные рефреши схлопываются в один in-flight промис (`refreshPromise`), чтобы не насиловать `/auth/refresh` при нескольких одновременных запросах.
- `authProvider.checkError` на `401`/`403` чистит токены и просит react-admin разлогинить пользователя.

## Почему кастомный `dataProvider`, а не `ra-data-simple-rest`

`ra-data-simple-rest` ожидает список записей как **голый JSON-массив**, а общее число — в HTTP-заголовке (`Content-Range`/аналог). Контракт же возвращает конверт `{ items: [...], total: N }` (см. `GET /nodes` в `openapi.yaml`) и постраничность через query-параметры `page`/`page_size`, а не через заголовки диапазона. Городить это через кастомный `httpClient`-хук поверх `ra-data-simple-rest` показалось не проще, чем написать ~120 строк прямого адаптера (`src/dataProvider.ts`) — он и читается прямолинейнее, и явно показывает, какие ресурсы реально протестированы (см. выше).

## Замечания к контракту

Оба замечания первого среза (`GET /cascades`/`GET /users` без `total`, неясность тела `POST /auth/logout`) **уже устранены выше по цепочке**: ветка `admin-client/scaffold` подтянула из `main` коммиты `2bac197` и `d3055d7`, которые унифицировали конверт списков (`total` теперь есть у `/nodes`, `/cascades`, `/users`) и уточнили `/auth/logout` (`refresh_token` — опциональное, но рекомендуемое поле тела запроса). Слить `main` в эту ветку было безопасно и сделано в рамках этого среза: `admin-client/` эти коммиты не трогают (только `contracts/`), конфликтов не было.

Важно для следующего, кто будет смотреть на эту ветку: если `src/contract/types.ts` когда-нибудь снова разойдётся с `../contracts/rest/openapi.yaml`, **не делайте вывод "контракт не менялся" по `git log -- contracts/...` только в этой ветке** — сверяйтесь с `git log main -- contracts/rest/openapi.yaml`, эта ветка могла снова отстать от `main`. Именно так ошибся один из параллельных треков в этом раунде.

Новых замечаний к контракту в этом срезе не возникло: формы `/cascades/{id}/test`, `/tests/{id}`, `/auth/change-password`, `TokenPair.must_change_password` вполне однозначны, реализация клиента следует им буквально.

## Scope этого среза / TODO

Реализовано в этом срезе (см. "Что реализовано" выше): ресурс `cascades`, реальный граф топологии, UI тест-запроса, принудительная смена пароля, `authProvider.logout` с телом запроса, ресурс `users`.

Сознательно остаётся вне этого среза:

- **Live-push статуса через WebSocket** (`WS /events`, TZ-6 §2/§4) — граф топологии и любой другой real-time UI сейчас держатся на поллинге (`GET /nodes`+`GET /cascades` каждые 5с, `src/topology/usePolling.ts`) вместо честного push, потому что эндпойнт `/events` на Platform ещё не реализован (подтверждено в этом раунде). Как только он появится — заменить `usePolling` на WS-подписку, обновляющую то же состояние; сам граф (`buildTopologyGraph`) менять не придётся, он уже не завязан на способ получения данных.
- **Сквозная проверка UI тест-запроса против живого Platform** — `POST /cascades/{id}/test`/`GET /tests/{id}` реализованы клиентом строго по контракту, но оба эндпойнта всё ещё `501 Not Implemented` на Platform (подтверждено отчётом трека Platform в этом раунде), так что `TestRequestButton` проверен только юнит/интеграционными тестами с мок-`fetch`, не против настоящего сервера. Довернуть, когда Platform выкатит эти два эндпойнта.
- **Графики потребления** (`/usage`, Recharts по ТЗ, TZ-6 §3.3) — сам эндпойнт на Platform тоже `501`; UI пользователей (`<Resource name="users">`) сейчас показывает только сущность/статус/привязанные каскады, без чисел потребления. Recharts не подключён.
- **UI ротации секретов** (TZ-6 §3.4) — не реализовано, зависит от эндпойнта ротации, которого пока нет в контракте.
- **MFA/TOTP-шаг логина** — поле `totp_code` уже уходит в `POST /auth/login`, но отдельного пошагового UI (запрос кода вторым шагом) нет; будет добавлено, когда Platform реализует и включит MFA (TZ-5 §6.3).
- **Кодогенерация типов из `openapi.yaml`** — `contracts/README.md` рекомендует генерировать типизированный клиент из схемы; типы (`src/contract/types.ts`) по-прежнему переписаны вручную. Набор вырос (auth + `Node` + `Cascade` + `LinkTest` + `User`) — со следующим ресурсом стоит подключить генератор (`openapi-typescript` и т.п.), ручное сопровождение уже ощутимо более трудоёмкое, чем в первом срезе.
- **Формы для `nodes`** (добавление в пул / назначение роли / вывод из эксплуатации, TZ-6 §3.1) — вне мандата этого среза (он был про `cascades`/топологию/тест-запрос/пароль/`users`); `nodes` остаётся list/show, как в первом срезе.
- **История тест-запросов по связке** (TZ-6 §3.2, "таблица истории") — контракт даёт только `GET /tests/{test_id}` (получение по id), эндпойнта со списком тестов по каскаду в `openapi.yaml` нет, так что таблицу истории строить не на чем; если понадобится — сначала контрактный вопрос к Platform, не задача клиента.
- **Code-splitting сборки** — один JS-чанк (~1.18 МБ до gzip, ~370 кБ после). Не проблема при текущем размере приложения, но стоит держать в уме при добавлении новых ресурсов/графиков (усложняется дальше добавлением Recharts под графики потребления).
