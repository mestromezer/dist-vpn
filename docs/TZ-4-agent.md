# ТЗ-4. Программа «Agent»

> Статус: техническое задание на разработку.
> Контекст: реализует роль «Agent» из [TZ-3-arhitektura-flota.md](TZ-3-arhitektura-flota.md), §2.1. Ставится на каждую VDS-ноду пула (входную или выходную — роль назначает Platform).
> Расположение: `C:\access\` (см. примечание в TZ-3 про сбой диска `D:`).

---

## 1. Назначение и границы ответственности

Agent — единственный компонент, который **напрямую** трогает Xray-core и Docker на конкретной VDS. Он:

- поднимает и держит живым локальный Xray-core в контейнере;
- исполняет команды, полученные от Platform (добавить/убрать inbound/outbound/пользователя/правило маршрутизации, переопределить балансировщик, ротировать секреты, поднять/поднять поверх Hop B туннель);
- отдаёт Platform телеметрию (health, байтовые счётчики, статус наблюдателя, результаты тест-запросов);
- **не хранит** долгосрочное состояние сам — при потере локальных данных (переустановка VDS, пересоздание контейнера) Agent должен суметь полностью восстановить рабочее состояние по команде от Platform, без ручного вмешательства.

Agent **не принимает решений** о топологии/failover самостоятельно — только исполняет команды и сообщает факты. Решения — на Platform (см. [TZ-5](TZ-5-platform.md)).

## 2. Технологический стек и обоснование

| Область | Выбор | Почему |
|---|---|---|
| Язык | Python 3.12+ | Явное предпочтение пользователя; совпадает с прецедентом [marznode](https://github.com/marzneshin/marznode) (тот же класс задачи: Python 3.12+, управление Xray/Hysteria/sing-box из агента) |
| Управление Docker | [docker-py](https://github.com/docker/docker-py) ([документация](https://docker-py.readthedocs.io/en/stable/)) | Официальный SDK для Docker Engine API — не переизобретать обвязку над `docker run`, как было в bash-версии (M5/M6) |
| Связь с Platform | gRPC (`grpcio`) + bidirectional streaming, **agent dial-out** | См. §4 — паттерн, а не готовая либа, обоснование ниже |
| Взаимная аутентификация | mTLS, готовые клиентские сертификаты от Platform/её CA | См. §5 |
| Управление Xray без рестарта | Нативные gRPC-стабы, сгенерированные из **собственных `.proto`-файлов Xray-core** (`app/proxyman/command`, `app/router/command`, `app/stats/command`) через `grpcio-tools` | Xray-core уже отдаёт `HandlerService`/`RoutingService`/`StatsService` по gRPC — сам CLI `xray api ...` (см. историю M5/M6) не более чем тонкая обёртка над этими вызовами (подтверждено чтением `main/commands/all/api/*.go` в исходниках). Вызывать нативно из Python — надёжнее и быстрее, чем шелл-эксек CLI/докер-контейнера ради каждой команды |
| Валидация конфигурации/команд | `pydantic` v2 | Стандарт де-факто в Python-экосистеме, совместим с gRPC-сообщениями через явный маппинг |
| Логирование | стандартный `logging` + JSON-форматтер (`python-json-logger`) | Структурированные логи для агрегации на Platform |
| Тестирование | `pytest`, `pytest-asyncio` | Стандарт |
| Упаковка/деплой | Docker-контейнер (тот же паттерн, что уже отработан для Xray: `Dockerfile`, `docker-compose.yml`) | Продолжение уже выбранного во всём проекте контейнерного подхода |
| Backhaul-транспорт Hop A↔Hop B (VDS1↔VDS2) | По умолчанию — то же VLESS+REALITY, что и раньше (уже отработано, ничего разрабатывать не нужно); опционально — **AmneziaWG** ([amnezia-vpn/amneziawg-go](https://github.com/amnezia-vpn/amneziawg-go)) как pluggable альтернатива | См. §6 — пользователь снял ограничение «обязательно VLESS» для этого хопа |

### Почему не Go (несмотря на то, что это типичный выбор для агентов класса Teleport/Consul)

Явное предпочтение пользователя — Python. Компенсация типичных минусов Python-агента (более тяжёлый рантайм, чем статический Go-бинарник) — Agent и так уже разворачивается в контейнере (весь проект контейнерный с самого начала), поэтому распространение single-binary не даёт того преимущества, которое даёт в других контекстах.

## 3. Функциональные требования

### 3.1. Жизненный цикл ноды

- **Bootstrap**: при первом запуске Agent генерирует локальный keypair, инициирует enrollment к Platform (получает mTLS-сертификат клиента — см. §5.2), сообщает о себе (hostname, IP, версия, доступные ресурсы).
- **Heartbeat**: периодическая (настраиваемый интервал, по умолчанию 15 с) отправка состояния через тот же gRPC-стрим — health локального Xray-контейнера, версия, uptime.
- **Restart-safe**: после перезапуска Agent переустанавливает соединение с Platform и запрашивает актуальное желаемое состояние (declarative reconciliation — Agent приводит фактическое состояние Xray к тому, что вернула Platform, а не полагается на то, что что-то сохранилось локально).

### 3.2. Исполнение команд от Platform (без рестарта Xray)

Переносится из уже проверенной части проекта (M5/M6), но теперь через нативный gRPC, а не CLI-обёртку:

| Операция | Xray gRPC-сервис/метод |
|---|---|
| Добавить/убрать inbound | `HandlerService.AddInbound` / `RemoveInbound` |
| Добавить/убрать outbound | `HandlerService.AddOutbound` / `RemoveOutbound` |
| Добавить/убрать пользователя в inbound | `HandlerService.AlterInbound` + `AddUserOperation`/`RemoveUserOperation` |
| Добавить/убрать правило маршрутизации | `RoutingService.AddRule` / `RemoveRule` (по `ruleTag`) |
| Переопределить/снять переопределение балансировщика | `RoutingService.OverrideBalancerTarget` |
| Статус балансировщика | `RoutingService.GetBalancerInfo` |
| Байтовые счётчики | `StatsService.QueryStats` / `GetStats` |

Примечание для реализации: `AlterInbound`/`AlterOutbound` существуют в протоколе (в отличие от CLI, который их не выводит — подтверждённый факт из M5) — Agent, работая напрямую с gRPC, может использовать их для смены пользователей на месте, где раньше (в bash-версии) приходилось делать add-new/remove-old.

### 3.3. Пресеты и ротация секретов (домен-логика, переносится из M1–M6)

- Agent умеет поднять любой из пресетов P1–P4 (VLESS/REALITY на RAW, XHTTP, gRPC; VLESS/TLS на WebSocket) по параметризованной команде от Platform — шаблоны конфигурации те же, что уже проверены и задокументированы в истории разработки (см. TZ-3 таблицу переносимых знаний).
- Ротация REALITY-ключей клиентских пресетов — двухфазно (новый inbound рядом со старым, Platform управляет моментом удаления старого — то же решение, что в M6, но координация теперь на Platform, а не в локальном `state.json`).
- Ротация TLS-сертификата P4 — специального кода не требует: по документации `CertificateObject.oneTimeLoading` (по умолчанию `false`) Xray **сам** перечитывает сертификат с диска (интервал ~3600 с) — Agent лишь кладёт новый файл, сертификат получен от Platform или через ACME-клиент, управляемый Agent'ом.

### 3.4. Тест-запрос (требование пользователя №2 — проверка канала)

По команде от Platform Agent обязан уметь:

1. Поднять эфемерный тестовый Xray-клиент (Docker-контейнер, тот же образ, что и основной Xray) с параметрами конкретного пресета/узла.
2. Выполнить HTTP-запрос через полученный SOCKS-прокси к контрольному URL.
3. Вернуть Platform **структурированный, человекочитаемый результат**: успех/неуспех, код ответа, задержка, на каком именно шаге отказ (не поднялся контейнер / TLS-хендшейк не прошёл / прокси не ответил / таймаут) — не просто "ok/fail", а достаточно данных, чтобы Platform и затем Admin Client могли показать администратору, **где именно** рвётся канал (см. требование к Platform/Admin Client в соответствующих ТЗ).

### 3.5. Отчётность/телеметрия

- Байтовые счётчики per-user/per-inbound/per-outbound — только объём, без адресов назначения (приватность, принцип не меняется относительно ранее согласованной модели).
- `log.access: "none"`, `dnsLog: false` — обязательное поле в каждом конфиге, который Agent генерирует, без исключений.
- Health локального Docker (жив ли контейнер Xray, ресурсы CPU/RAM/диск).

## 4. Требования к производительности

- Heartbeat/телеметрия не должны создавать заметную нагрузку — интервал и объём данных должны быть настраиваемыми, значение по умолчанию рассчитано на пул до нескольких десятков нод на одну Platform без деградации (конкретные числа — уточнить нагрузочным тестированием на этапе реализации, не выдумывать здесь голые цифры).
- Применение команд (add/remove inbound/outbound/user) — без разрыва существующих активных соединений пользователей, кроме случаев, когда команда прямо предписывает убрать конкретный inbound/outbound (ожидаемое поведение, не баг).
- Тест-запрос (§3.4) не должен занимать больше нескольких секунд сверх времени, необходимого на сетевой RTT и поднятие эфемерного контейнера — деградация замеряется на этапе реализации.
- Agent должен переживать кратковременную потерю связи с Platform (network partition) без падения локального Xray и без потери накопленной, ещё не отправленной телеметрии дольше разумного буфера (нужно ограничение по памяти на этот буфер, конкретное значение — на этапе реализации).

## 5. Требования к безопасности

### 5.1. Принцип: Agent не принимает входящих соединений для control-plane

Основано на архитектуре reverse-tunnel Teleport ([Teleport Agent Architecture](https://goteleport.com/docs/reference/architecture/agents/)): агент **сам** устанавливает исходящее соединение к Platform и держит его открытым (gRPC bidi-stream) для получения команд — Platform не открывает соединение к агенту напрямую. Преимущество, задокументированное в самой природе паттерна: агент может находиться за NAT/файрволом, **не публикуя ни одного входящего порта для управления вообще** (кроме портов пресетов Hop A/Hop B, которые и так должны быть открыты по своей природе — обычные VLESS-порты, замаскированные под HTTPS).

### 5.2. Взаимная аутентификация — mTLS, а не голые токены

- Соединение Agent↔Platform — обязательно mTLS (см. [gRPC Authentication guide](https://grpc.io/docs/guides/auth/), примеры реализации: [python-grpc-mutual-tls-auth](https://github.com/nikolskiy/python-grpc-mutual-tls-auth), [python-grpc-ssl](https://github.com/joekottke/python-grpc-ssl)).
- Сертификаты — короткоживущие, с автоматическим продлением, выпущены собственным приватным CA. Рекомендация — не изобретать свой PKI-код, а поднять готовый CA: [step-ca / smallstep/certificates](https://github.com/smallstep/certificates) — умеет автоматизированный выпуск/продление X.509-сертификатов именно для этого класса задач ("DevOps mTLS everywhere").
- Долгосрочный секрет ноды хранится **только** в момент bootstrap (enrollment token с TTL и одноразовым использованием) — после первичной выдачи сертификата токен становится бесполезен.

### 5.3. Секреты на диске

- Приватные ключи (mTLS-клиент, REALITY) — права доступа `600`, отдельный непривилегированный пользователь/группа для процесса Agent, не root внутри контейнера.
- Ни один секрет не пишется в открытом виде в логи (структурированное логирование должно явно исключать поля с ключами — аналог `no_log: true` из практики Ansible, см. [Ansible Vault secrets best practices](https://oneuptime.com/blog/post/2026-02-21-how-to-manage-ansible-secrets-best-practices/view) — тот же принцип применим независимо от конкретного инструмента).

### 5.4. Docker socket

- Agent обращается к Docker Engine API (через `docker-py`) для управления **только** контейнером(-ами) Xray, которые сам же и создал — не через примонтированный `/var/run/docker.sock` внутрь недоверенного контейнера (тот приём был приемлем для одноразового bash-оркестратора в прототипе, но для production-агента предпочтительно: Agent либо запускается на хосте напрямую (не в контейнере) с доступом к Docker, либо — если тоже в контейнере — получает доступ к сокету по минимально необходимым правам, эта развилка — предмет решения на этапе детальной реализации, с явным протоколированием выбора и его обоснования).

### 5.5. Чек-лист по распространённым ошибкам (проекция OWASP Top 10 на Agent)

| OWASP Top 10:2021 категория | Как учитывается в Agent |
|---|---|
| [A02 Cryptographic Failures](https://owasp.org/Top10/2021/) | Только mTLS для control-plane, только актуальные шифры (см. §5.2), никаких самодельных схем шифрования |
| [A05 Security Misconfiguration](https://owasp.org/Top10/2021/) | `log.access:"none"` и минимальные права — обязательные, не опциональные значения по умолчанию |
| [A06 Vulnerable and Outdated Components](https://owasp.org/Top10/2021/) | Пины версий зависимостей с хэшами (`pip-compile`, см. рекомендацию из [FastAPI best practices](https://fastlaunchapi.dev/blog/fastapi-best-practices-production-2026)), регулярный CVE-скан образа |
| [A09 Security Logging and Monitoring Failures](https://owasp.org/Top10/2021/) | Структурированные логи, отправка health/событий на Platform — само наличие Agent-агента это и закрывает по конструкции |

## 6. Backhaul-транспорт Hop A↔Hop B (VDS1↔VDS2) — пользователь снял жёсткое требование VLESS

Формулировка задачи прямо говорит: «для связи от первой vds до второй нет ограничений — канал может быть любым, VLESS важен только для клиента». Architecturally это значит: Agent должен трактовать транспорт Hop B как **плагин**, а не как нечто, намертво зашитое в код (в отличие от Hop A, где VLESS/REALITY обязателен, т.к. напрямую обращён к клиенту и должен маскироваться под HTTPS перед лицом систем DPI-инспекции трафика).

Варианты (не взаимоисключающие — можно поддержать оба, выбор — по конфигурации от Platform):

1. **VLESS+REALITY chaining** (по умолчанию, "если не чинится — не трогай") — уже полностью проработано и задокументировано в истории проекта, требует нуля новой разработки.
2. **AmneziaWG** ([amnezia-vpn/amneziawg-go](https://github.com/amnezia-vpn/amneziawg-go)) — форк WireGuard-Go, специально созданный для устойчивости к DPI (в отличие от ванильного WireGuard, чей хендшейк уверенно фингерпринтится — это и есть причина не брать ванильный WireGuard, раз Hop B тоже пересекает границу целевого региона и попадает под ту же DPI-инспекцию, что и Hop A). Плюсы: ядро-уровневая производительность, значительно проще конфигурация точка-точка, чем VLESS-цепочка. Управление интерфейсом со стороны Agent — через стандартные `wg`/`awg` CLI-инструменты (subprocess) либо через netlink напрямую ([pyreguard](https://github.com/stevekerrison/pyreguard) как пример Python-библиотеки для этого, если потребуется более программный доступ, чем вызов CLI).

Решение, какой вариант использовать по умолчанию в production, — на этапе реализации, но **интерфейс Agent'а к backhaul-транспорту должен быть спроектирован как abstraction (стратегия), а не как хардкод VLESS**, чтобы переключение было конфигурационным решением Platform, а не переписыванием Agent'а.

## 7. Требования к удобству эксплуатации

- Один бинарный образ Docker для Agent, единая точка конфигурации при первом запуске (адрес Platform + enrollment-токен — минимум, что нужно оператору руками ввести/передать).
- Понятные структурированные логи (не «многословный debug», а уровни: что произошло, что делает Agent сейчас, что пошло не так — с достаточным контекстом для диагностики без чтения исходного кода).
- Самодиагностика при старте: явное сообщение, если недоступен Docker, недоступна Platform, испорчен локальный сертификат — вместо тихого зависания.

## 8. Критерии приёмки

- [ ] Agent разворачивается как Docker-контейнер, при первом запуске проходит enrollment к Platform по одноразовому токену и получает mTLS-сертификат.
- [ ] Agent способен исполнить полный набор операций из §3.2 без рестарта локального Xray (проверяется тем же способом, что и в M5/M6: сквозной curl через клиент не прерывается на время применения совместимых изменений).
- [ ] Agent исполняет тест-запрос (§3.4) и возвращает результат, различающий как минимум: успех / контейнер не поднялся / TLS-хендшейк не прошёл / прокси не ответил / таймаут.
- [ ] Ни один секрет (приватный ключ, mTLS-сертификат) не появляется в логах Agent'а в открытом виде.
- [ ] Agent переживает потерю связи с Platform на разумный период без падения локального Xray и восстанавливает канал управления сам, без ручного вмешательства.
- [ ] Backhaul-транспорт Hop B выбирается конфигурацией, а не хардкодом — продемонстрировано минимум на двух вариантах (VLESS-chaining и один из альтернативных).
