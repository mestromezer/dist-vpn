# ТЗ-6. Программа «Admin Client»

> Статус: техническое задание на разработку.
> Контекст: реализует роль «Admin Client» из [TZ-3-arhitektura-flota.md](TZ-3-arhitektura-flota.md), §2.3. Единственный интерфейс администратора к [Platform](TZ-5-platform.md).

---

## 1. Назначение и границы ответственности

Admin Client — витрина поверх REST/WebSocket API Platform. **Не хранит** и не принимает никаких решений сам — всё состояние и вся бизнес-логика (сборка каскадов, failover, ротация) — на Platform. Задача Admin Client — показать это состояние человеку понятно и дать интерфейс для команд, которые Platform умеет исполнять.

Явное требование пользователя: *«клиентское приложение должно писать по минимуму кода, использовать библиотеки компонент и другие средства для production-ready разработки. Кастомные стили — только при крайней необходимости»*. Это прямо определяет технологический выбор ниже — не потому что "так модно", а потому что задача явно требует минимизировать объём кастомного кода.

---

## 2. Технологический стек и обоснование

| Область | Выбор | Обоснование / источник |
|---|---|---|
| Язык/сборка | TypeScript + Vite | Стандарт для современных SPA, типобезопасность против ошибок в работе с API |
| Framework для admin-панели | [react-admin](https://github.com/marmelab/react-admin) | Специализированный, зрелый (маркировка проекта — фреймворк именно для admin-панелей/внутренних инструментов поверх REST/GraphQL API), минимальный бойлерплейт "из коробки" для CRUD-экранов (список/форма/фильтры/пагинация уже готовы) — прямое попадание в требование "писать минимум кода". По сравнению с более гибкой, но требующей больше самостоятельного кода альтернативой [Refine](https://github.com/refinedev/refine) (headless-подход, свобода выбора UI-кита, но больше кода на ту же фичу — см. сравнение [react-admin vs Refine](https://refine.dev/blog/react-admin-vs-refine/) и [React-Admin vs Refine: Feature Comparison (Marmelab)](https://marmelab.com/blog/2023/07/04/react-admin-vs-refine.html)) — для этой задачи важнее скорость получения готового результата, чем гибкость смены UI-кита |
| UI-компоненты/дизайн-система | Material UI (входит в react-admin "из коробки") | Собственных кастомных стилей не требуется почти нигде — react-admin уже построен на MUI, что прямо закрывает требование "кастомные стили только при крайней необходимости" |
| Визуализация топологии каскадов (требование №2 — "где обрывается соединение") | [React Flow / xyflow](https://reactflow.dev/) | Готовая, широко используемая библиотека именно для узел-рёберной визуализации графов состояния (используется в т.ч. крупными продуктами — см. примеры на [reactflow.dev](https://reactflow.dev/) и обзор [React Flow: Everything you need to know](https://www.synergycodes.com/blog/react-flow-everything-you-need-to-know)); ноды = VDS, рёбра = связки Hop A/Hop B, цвет ребра/узла = статус из `HealthEvent`/`Cascade.status` (Platform, §4.3 ТЗ-5) |
| Графики потребления | Recharts (стандартный выбор для интеграции с React-экосистемой, применяется в примерах самого react-admin) | Не писать визуализацию графиков с нуля |
| Получение/кэширование данных | Встроенный data-provider слой react-admin (построен поверх принципов, аналогичных [TanStack Query](https://tanstack.com/query)) | Не писать свой слой кэширования/инвалидации запросов |
| Real-time обновления | Нативный WebSocket API браузера + подписка, обновляющая data-provider react-admin/состояние React Flow | Соответствует WebSocket-эндпойнту Platform (§4.3, §7 ТЗ-5) |
| Аутентификация (клиентская часть) | `authProvider` react-admin поверх `/auth/login`/`/auth/refresh` Platform | Не писать собственный экран логина и хранение токена с нуля — паттерн уже есть в фреймворке |

## 3. Функциональные требования

### 3.1. Управление нодами и каскадами

- Список нод (таблица react-admin: статус, роль, регион, последний heartbeat) с фильтрами/поиском "из коробки".
- Форма добавления ноды в пул / назначения роли / вывода из эксплуатации.
- **Визуализация каскадов как графа** (React Flow): входная нода → пул выходных нод-кандидатов, статус каждой связки — цветом (зелёный/жёлтый/красный) и коротким текстом причины при наведении — прямое выполнение требования пользователя №2 ("отображать какие связки работают, где обрывается соединение... понятным человеку").

### 3.2. Тест-запрос

- Кнопка "проверить канал" на конкретной связке/пресете → вызывает `POST /cascades/{id}/test` (ТЗ-5, §7) → результат отображается **не как голый JSON**, а как понятный человеку статус: успех с задержкой, либо явное указание этапа отказа (например: "Не удалось поднять тестовый клиент на ноде X" / "TLS-хендшейк не прошёл" / "Прокси не ответил за N секунд") — ровно то, что возвращает Platform согласно ТЗ-5 §4.3.
- История тест-запросов по связке — таблица (готовый компонент react-admin `<List>`, без кастомной вёрстки).

### 3.3. Управление пользователями

- CRUD пользователей VPN, привязка к каскадам/пресетам.
- Отображение потребления (объём) на карточке пользователя — только числа/графики, никогда не адреса назначения (клиент физически не получает от Platform ничего иного — см. ТЗ-5 §6.4, гарантия на уровне архитектуры, а не только UI).

### 3.4. Ротация секретов

- Кнопка запуска ротации (Hop A/Hop B/сертификат P4) с подтверждением, статус в реальном времени (та же WebSocket-подписка).

### 3.5. Аутентификация администратора

- Экран логина (готовый `authProvider`-паттерн react-admin), поддержка MFA/TOTP-шага, если включён на Platform (см. ТЗ-5 §6.3).
- Автоматический logout при истечении сессии, авто-обновление access-токена через refresh (стандартный паттерн `authProvider`, не самописный).

## 4. Требования к производительности

- Первая отрисовка списка нод/пользователей — не должна требовать полной загрузки всех записей разом: пагинация из коробки (react-admin уже это умеет по умолчанию).
- Граф топологии (React Flow) должен оставаться отзывчивым при разумном числе нод в пуле (десятки–сотни узлов) — это стандартная зона ответственности библиотеки, не кастомного кода.
- Real-time обновления статуса не должны требовать перезагрузки страницы или полного повторного запроса всего состояния — точечное обновление конкретной ноды/связки в уже отрисованном графе/таблице.

## 5. Требования к безопасности

Клиентское приложение — не место для кастомной криптографии или самодельной логики авторизации; следующий список — это в первую очередь **что не писать самому**, а не что писать:

| Риск | Мера |
|---|---|
| XSS ([OWASP A03 в контексте клиента](https://owasp.org/Top10/2021/)) | React по умолчанию экранирует вывод в JSX — не использовать `dangerouslySetInnerHTML` без крайней необходимости и без явной санитизации |
| Небезопасное хранение токена (см. ТЗ-5 §6.3) | Следовать выбранной на Platform схеме (httpOnly cookie или токен в памяти, не `localStorage` для чувствительных долгоживущих токенов) |
| CSRF (если используются cookie) | `SameSite=Strict/Lax` на cookie + CSRF-токен, если Platform выбирает cookie-based сессию — координируется с ТЗ-5 |
| Уязвимые зависимости фронтенда ([A06](https://owasp.org/Top10/2021/)) | `npm audit`/эквивалент в CI, лок-файл коммитится, регулярное обновление |
| Утечка чувствительных данных в собранный бандл (ключи API и т.п.) | Никаких секретов в клиентском коде/переменных окружения фронтенда — только публичный адрес API Platform |
| Отсутствие HTTPS | Клиент обслуживается только по HTTPS в production, без исключений |

---

## 6. Требования к удобству (UX)

- Минимум кастомных стилей — используется дизайн-система MUI, поставляемая с react-admin, кастомизация — через тему (theme), а не точечные CSS-переопределения.
- Понятные, человекочитаемые статусы везде, где Platform возвращает структурированную причину отказа (§3.2) — не выводить признаки ошибок в виде кодов/JSON без перевода в текст.
- Доступность (accessibility) — наследуется от MUI/react-admin "из коробки" (компоненты уже соответствуют базовым практикам ARIA), дополнительных усилий не требуется сверх использования штатных компонентов.

---

## 7. Критерии приёмки

- [ ] Admin Client разворачивается и работает поверх API Platform без написания собственного слоя аутентификации/кэширования данных с нуля (используются `authProvider`/data-provider react-admin).
- [ ] Граф каскадов отображает статус связок в реальном времени, включая явный визуальный сигнал "где обрывается соединение".
- [ ] Результат тест-запроса отображается человеку понятным текстом с указанием места отказа, а не JSON/кодом ошибки.
- [ ] Все CRUD-экраны (ноды, пользователи, каскады) собраны стандартными компонентами react-admin, кастомный CSS-код отсутствует либо сведён к минимальной теме.
- [ ] Проверка по чек-листу §5 проведена вручную перед сдачей (в т.ч. отсутствие секретов в собранном бандле — `grep`/анализ итогового билда).
