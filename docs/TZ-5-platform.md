# ТЗ-5. Программа «Platform»

> Статус: техническое задание на разработку.
> Контекст: реализует роль «Platform» из [TZ-3-arhitektura-flota.md](TZ-3-arhitektura-flota.md), §2.2. Центральный сервер управления пулом Agent'ов ([ТЗ-4](TZ-4-agent.md)), источник истины для топологии, пользователей и мониторинга; отдаёт API для Admin Client ([ТЗ-6](TZ-6-admin-client.md)).

---

## 1. Назначение и границы ответственности

Platform — единственный компонент, который **знает** всё: реестр нод, реестр пользователей, топологию каскадов, историю ротаций, историю health-событий. Agent'ы и Admin Client сами по себе состояния не хранят (Agent — исполнитель и репортёр, Admin Client — витрина поверх API Platform).

Platform:
- принимает регистрацию (enrollment) новых Agent'ов и выдаёт им mTLS-сертификаты (см. §6.2);
- хранит и применяет топологию: какие входные ноды с какими выходными связаны в каскад, рассылает Agent'ам соответствующие команды;
- реагирует на потерю health-сигнала от ноды: для кратковременных сбоев полагается на уже нативный failover Xray (`balancer`+`observatory`, работает **внутри** уже собранного каскада без участия Platform); для длительной недоступности/явного вывода ноды — переконфигурирует каскад;
- централизованно управляет пользователями (создание/отзыв/учёт потребления), рассылая соответствующие команды затронутым Agent'ам;
- агрегирует телеметрию и результаты тест-запросов, отдаёт их Admin Client в виде, понятном человеку (требование пользователя №2 — см. §4.3);
- отдаёт REST/WebSocket API для Admin Client, с полноценной аутентификацией администратора (требование пользователя №5).

## 3. Модель данных (минимальный набор сущностей)

| Сущность | Назначение |
|---|---|
| `Node` | Нода пула: id, роль (entry/exit/универсальная), регион, статус (`ENROLLING`/`HEALTHY`/`DEGRADED`/`DOWN`/`DECOMMISSIONED`), версия Agent'а, последний heartbeat |
| `Cascade` | Связка входной ноды с набором нод-кандидатов на выход (пул Hop B, аналог `foreign-balancer` из ранее проверенной модели), выбранный пресет(ы) Hop A |
| `User` | Человек: id, email/имя, UUID(ы) для подключения, к каким каскадам/пресетам имеет доступ, дата создания/отзыва |
| `UsageStat` | Байтовый счётчик (uplink/downlink) — per-user/per-node/per-timeframe. Только числа, без адресов назначения (принцип приватности не меняется, см. TZ-3 §5) |
| `HealthEvent` | Журнал переходов состояния (нода/каскад: UP→DOWN, DOWN→UP, с таймстампом и причиной) — источник данных для требования №2 ("что и где отвалилось") |
| `LinkTest` | Результат тест-запроса (см. §4.3): каскад/нода, момент запуска, итог, задержка, шаг отказа, кто инициировал (администратор вручную / расписание) |
| `RotationRecord` | История ротаций секретов: что, когда, кем/чем инициировано, успех/откат |
| `AdminAccount` | Учётная запись администратора: логин, хэш пароля (Argon2id), включена ли MFA, роль |

## 4. Функциональные требования

### 4.1. Управление пулом нод

- Приём enrollment-запроса от нового Agent'а (по одноразовому токену, см. ТЗ-4 §5.2), выпуск mTLS-сертификата, регистрация в реестре со статусом `ENROLLING` → `HEALTHY` после первого успешного heartbeat.
- Назначение/смена роли ноды (entry/exit) администратором.
- Вывод ноды из эксплуатации (`DECOMMISSIONED`) — Platform обязана переконфигурировать все каскады, где эта нода участвовала, до реального отключения (не оставлять «висящие» ссылки).

### 4.2. Сборка каскадов и failover

- Администратор указывает: эта входная нода использует вот этот пул выходных нод-кандидатов.
- Platform транслирует это в команды конкретным Agent'ам (добавить outbound/inbound с соответствующими ключами — переиспользуется схема из ранее проверенной модели: балансировщик с префиксным `selector`, `observatory`, `fallbackTag`).
- Кратковременная недоступность одной выходной ноды **не требует** вмешательства Platform — нативный `balancer`+`observatory` внутри уже собранного каскада справляется сам (этот факт уже был подтверждён ранее в проекте и переносится как архитектурное решение, не переизобретается).
- Длительная недоступность (порог — настраиваемый таймаут отсутствия heartbeat) или явный вывод ноды — Platform убирает ноду из пула кандидатов через Agent (`RemoveOutbound`/аналог), и, если задан резерв — включает следующую доступную ноду.

### 4.3. Мониторинг связок и обрывов, тест-запрос (требование пользователя №2 — приоритетное)

Явная формулировка задачи: *«нужно отображать статистику какие связки работают, где обрывается соединение, возможность тестового запроса для проверки канала с отображением понятным человеку. Система должна чётко следить что и где отвалилось, чтобы можно было управлять переключением конфигов»*. Конкретно Platform обязана:

- Хранить **состояние каждой связки** (пара вход↔выход, а также сам пресет Hop A) как явную сущность с текущим статусом, а не выводить его на лету из разрозненных счётчиков — это `Cascade.status` + связанные `HealthEvent`.
- Инициировать тест-запрос (§3.4 ТЗ-4) по требованию администратора **на конкретную связку** через API, и отдавать результат в структурированном виде: успех/неуспех + **этап**, на котором произошёл сбой (не смог поднять тестовый клиент / TLS-хендшейк / прокси не ответил / таймаут вышестоящего запроса) — этого достаточно, чтобы Admin Client показал человеку понятную причину, а не голый "ошибка".
- Вести журнал `HealthEvent` с точным временем перехода состояния и причиной — чтобы можно было посмотреть **историю**, а не только текущий момент ("отвалилось в 14:32, из-за таймаута наблюдателя на выходной ноде X").
- Отдавать эти данные через WebSocket в реальном времени (push, не только по запросу) — Admin Client должен обновлять статус без ручного обновления страницы.
- API должен явно разделять "объём трафика" (приватная статистика пользователей, см. §4.4) и "здоровье канала" (эта секция) — не смешивать в одной модели данных.

### 4.4. Управление пользователями и приватный мониторинг потребления

Переносится из ранее согласованной и уже проверенной модели (переносится принцип, не код):

- Создание пользователя → Platform выбирает, к каким пресетам/каскадам у него должен быть доступ, рассылает `AddUserOperation` соответствующим Agent'ам с **тем же UUID** на все затронутые ноды.
- Отзыв доступа → `RemoveUserOperation` на всех затронутых нодах.
- UUID пользователя не меняется при ротации серверных секретов (принцип из ранее сделанного M6 остаётся).
- Учёт потребления — **только байтовые счётчики**, агрегируемые из телеметрии Agent'ов; Platform не хранит и не может хранить содержимое/адреса назначения трафика пользователей — это гарантируется тем, что сами Agent'ы никогда не отправляют ничего, кроме чисел (закладывается ещё на уровне конфигурации Xray — `log.access:"none"`, только `stats`/`metrics`).

### 4.5. Ротация секретов

- Ручной запуск администратором либо по расписанию (через ARQ) — та же двухфазная модель для клиентских REALITY-пресетов (новое рядом со старым, отзыв старого по подтверждению/после okончания grace-периода) и тривиальная модель для TLS-сертификата P4 (просто заменить файл, Xray сам подхватит).

## 5. Требования к производительности

- REST API — время ответа на типовые операции чтения (список нод/пользователей/каскадов) не должно деградировать заметно при росте пула до нескольких десятков/сотен нод и пользователей — обеспечивается индексами БД и пагинацией списков по умолчанию (не отдавать неограниченные списки одним запросом).
- WebSocket-канал статуса должен выдерживать множественные одновременные подключения администратора(-ов) без потери сообщений (буферизация/переподключение на стороне клиента — см. ТЗ-6).
- gRPC-сервер для Agent'ов — рассчитан на постоянное количество открытых bidi-стримов, равное числу нод в пуле; необходимо здоровое ограничение на размер сообщения/буферов, чтобы одна перегруженная нода не деградировала обслуживание остальных.
- Фоновые задачи (ротации, периодические проверки) — через ARQ с ограничением конкурентности, чтобы массовая ротация по всему пулу не создавала пиковую нагрузку на все ноды одновременно (искусственно размазывать по времени).

## 6. Требования к безопасности

### 6.1. Общий подход

Каждое требование ниже явно спроецировано на конкретную рекомендацию из [OWASP Top 10:2021](https://owasp.org/Top10/2021/) и/или [OWASP Application Security Verification Standard (ASVS)](https://owasp.org/www-project-application-security-verification-standard/) (актуальная версия 5.0.0, май 2025; репозиторий — [OWASP/ASVS на GitHub](https://github.com/OWASP/ASVS)) — как явно и было потребовано ("проверить через список популярных ошибок при построении приложения с учётными записями").

### 6.2. Agent↔Platform (машинная аутентификация)

- Только mTLS, только через собственный CA ([step-ca](https://github.com/smallstep/certificates)); голых bearer-токенов между Agent и Platform быть не должно.
- Enrollment-токен — одноразовый, с TTL, инвалидируется сразу после использования (иначе перехват токена = постоянный доступ, классическая ошибка A07 Identification and Authentication Failures).
- Сертификаты — короткоживущие с автопродлением, а не "выписали один раз на 10 лет и забыли" — снижает ущерб от компрометации конкретной ноды.

### 6.3. Admin Client↔Platform (человеческая аутентификация) — против типовых ошибок

Явно спроецировано на OWASP-рекомендации:

| Типовая ошибка (по OWASP) | Мера в Platform |
|---|---|
| Хранение паролей в открытом/слабо хэшированном виде ([A02 Cryptographic Failures](https://owasp.org/Top10/2021/)) | Argon2id, параметры по [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) (не bcrypt — тот рекомендован только для legacy) |
| Долгоживущие access-токены без возможности отзыва | Access-токен 15–30 минут, refresh-токен с ротацией и deny-list по `jti` при компрометации — практика описана в [JWT Cheat Sheet / OAuth2 Cheat Sheet OWASP](https://cheatsheetseries.owasp.org/cheatsheets/JSON_Web_Token_Cheat_Sheet.html) |
| Хранение JWT в `localStorage`, уязвимое к XSS | Access-токен — в httpOnly Secure cookie **или**, если Admin Client — SPA с Bearer-токеном в памяти (не localStorage) — решение фиксируется на этапе реализации, но localStorage для долгоживущих токенов — запрещено этим ТЗ |
| Отсутствие лимита попыток входа (credential stuffing/brute force) | `slowapi`, лимит на IP и на логин отдельно (см. пример конфигурации "100 запросов/минуту на IP" из [FastAPI Best Practices for Production 2026](https://fastlaunchapi.dev/blog/fastapi-best-practices-production-2026) как отправная точка, подбирается под реальный профиль использования) |
| Broken Access Control ([A01](https://owasp.org/Top10/2021/)) | Каждый API-эндпойнт — явная проверка роли/прав на уровне зависимости FastAPI (`Depends`), а не полагание на то, что "в UI кнопки не видно" |
| Отсутствие MFA для единственной учётной записи с полным доступом | TOTP (стандартный протокол, библиотеки `pyotp`) — обязателен как минимум для встроенной административной учётной записи, если она одна на всю систему |
| Небезопасная конфигурация по умолчанию ([A05 Security Misconfiguration](https://owasp.org/Top10/2021/)) | Дефолтный пароль администратора генерируется случайно при первом деплое и требует немедленной смены — не хардкодится и не документируется публично |
| SSRF ([A10](https://owasp.org/Top10/2021/)) | Особенно актуально для функции тест-запроса (§4.3) — она инициирует сетевые запросы по команде администратора; целевой URL для тест-запроса должен быть либо фиксирован конфигурацией, либо валидироваться против allow-list, не приниматься произвольным от клиента без ограничений |
| Уязвимые/устаревшие зависимости ([A06](https://owasp.org/Top10/2021/)) | `pip-compile` с хэшами + регулярный CVE-скан, как и в Agent |
| Недостаточное логирование попыток входа/действий администратора ([A09](https://owasp.org/Top10/2021/)) | Аудит-лог всех административных действий (кто, что, когда) — отдельно от приватной статистики пользователей (не смешивать!) |

### 6.4. Данные пользователей VPN

- Platform физически не получает от Agent'ов ничего, кроме байтовых счётчиков — это гарантия архитектуры (Agent не отправляет иного), а не политика, которую можно молча нарушить на уровне Platform.
- Доступ к данным о потреблении конкретного пользователя — та же ролевая модель, что и остальные данные (§6.3, Broken Access Control).

## 7. API (высокоуровнево, детальная OpenAPI-схема — на этапе реализации)

- `POST /auth/login`, `POST /auth/refresh`, `POST /auth/logout` (с инвалидацией refresh-токена).
- `GET/POST/PATCH/DELETE /nodes` — CRUD нод, назначение ролей.
- `GET/POST/PATCH/DELETE /cascades` — сборка каскадов.
- `GET/POST/DELETE /users` — управление пользователями VPN.
- `GET /usage` — агрегированная статистика потребления (только объём).
- `POST /cascades/{id}/test` — инициировать тест-запрос, `GET /cascades/{id}/tests` — история.
- `WS /events` — потоковые обновления статуса нод/каскадов в реальном времени.
- Полная OpenAPI-схема генерируется FastAPI автоматически — Admin Client может использовать её для типобезопасной генерации клиента (см. ТЗ-6).

## 8. Требования к удобству эксплуатации

- Автогенерируемая OpenAPI/Swagger-документация (встроена в FastAPI из коробки) — не поддерживать отдельный документ руками.
- Единая команда развёртывания (`docker compose up`), миграции применяются автоматически при старте (Alembic).
- Структурированные логи с уровнями, разделение access/error, как и в Agent.
- Чёткое сообщение об ошибке при недоступности БД/Redis при старте — вместо тихого зависания.

## 9. Критерии приёмки

- [ ] Новый Agent проходит enrollment и появляется в реестре нод со статусом `HEALTHY` после первого heartbeat.
- [ ] Администратор может собрать каскад (входная нода + пул выходных) через API, и это приводит к реальным командам на Agent'ах (проверяется тем же способом, что и раньше: сквозной curl через тестового клиента).
- [ ] Кратковременное падение одной выходной ноды не требует вмешательства Platform — сквозной канал продолжает работать через нативный failover.
- [ ] Длительное падение/явный вывод ноды из пула приводит к её удалению из конфигурации связанных каскадов через Agent, без ручного редактирования конфигов.
- [ ] Тест-запрос по конкретной связке возвращает результат с указанием этапа отказа, если канал не работает — не просто "ошибка".
- [ ] `HealthEvent`-журнал фиксирует переходы состояния с точным временем и причиной, доступен через API.
- [ ] Admin Client получает обновления статуса через WebSocket без необходимости вручную обновлять страницу.
- [ ] Полный цикл входа администратора, включая rate-limiting при переборе пароля и обязательную смену дефолтного пароля при первом входе, — проверен вручную по пунктам §6.3.
- [ ] Ни при каких обстоятельствах Platform не получает и не хранит содержимое/адреса назначения пользовательского трафика — проверяется по факту отсутствия таких полей в модели данных и в реальном трафике Agent→Platform.
