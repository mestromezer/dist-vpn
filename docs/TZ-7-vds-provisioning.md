# ТЗ-7. Подготовка VDS перед установкой Agent (provisioning)

> Статус: техническое задание на разработку.
> Контекст: разовая процедура ввода новой VDS (РФ или зарубежной) в пул — после покупки/выбора (критерии выбора РФ-VDS не меняются, см. `TZ-1-rossiyskiy-vds.md`), до установки [Agent](TZ-4-agent.md) и подключения к [Platform](TZ-5-platform.md).

---

## 1. Назначение и границы ответственности

Эта задача явно отделена от Agent (ТЗ-4): Agent управляет Xray и общается с Platform, а provisioning — это то, что делает чистую VDS от хостера пригодной и безопасной для того, чтобы на неё вообще можно было поставить Agent. Выполняется **один раз** при вводе ноды в эксплуатацию (и при необходимости — переиспользуется для пересоздания ноды с нуля).

---

## 2. Требование №1 пользователя: production-ready хранение и выполнение скриптов

Явная формулировка задачи: *«Production-ready хранение скриптов (если будут использоваться). Это важный аспект безопасности, найти референсы больших приложений и посмотреть как там сделано»*. Разбор реальных референсов и итоговое решение:

### 2.1. Инструмент — Ansible, а не россыпь bash-скриптов

Референс: сама индустриальная практика хранения секретов для provisioning-инструментов построена вокруг **декларативных, идемпотентных** описаний состояния сервера, а не императивных bash-скриптов, склеенных вручную. [Ansible](https://www.ansible.com/) — зрелый, много лет используемый в продакшене выбор именно для этого класса задач (подготовка серверов), с готовой моделью хранения секретов ([Ansible Vault](https://oneuptime.com/blog/post/2026-02-21-how-to-manage-ansible-secrets-best-practices/view), [DigitalOcean: Use Ansible Vault to Protect Sensitive Playbook Data](https://www.digitalocean.com/community/tutorials/how-to-use-vault-to-protect-sensitive-ansible-data)):

- Ansible Vault шифрует секреты AES-256 (CTR + HMAC-SHA256, ключ через PBKDF2) — конкретные детали задокументированы, не "самодельное шифрование".
- Пароль от Vault хранится **отдельно от репозитория** (файл с правами `600`, в `.gitignore`), не в коде.
- В CI/CD пароль Vault передаётся как секрет пайплайна, пишется во временный файл на время выполнения и удаляется после — практика прямо описана в референсах выше.
- Важное ограничение (задокументировано, не наше открытие): Vault защищает секреты **на диске**, но не даёт разграничения доступа между людьми, знающими общий пароль, и не защищает секреты в памяти во время выполнения — если нужно более тонкое разграничение или secrets rotation на уровне организации, следующий шаг — внешний секрет-менеджер (HashiCorp Vault, AWS Secrets Manager).
- Альтернатива/дополнение — [Mozilla SOPS](https://github.com/getsops/sops) + [age](https://github.com/FiloSottile/age): шифрует **отдельные значения** внутри YAML/JSON, а не файл целиком — итоговый diff в git показывает, какой именно ключ поменялся, без раскрытия значения. Рекомендуется, если провижининг-переменные и так лежат в YAML/JSON (типичный формат Ansible `vars`) и важна читаемая история изменений в git.

**Решение для этой задачи**: Ansible playbook'и хранятся в git (то же репо, что и остальной проект), секреты — через Ansible Vault (простой случай, один администратор) либо SOPS+age (если понадобится более гранулярная история изменений секретов в git). Никаких голых паролей/токенов в самих playbook'ах или в README.

### 2.2. Явный запрет на антипаттерн `curl | bash`

Референсы, подтверждающие статус этого паттерна как известного риска: [Sysdig — Friends don't let friends Curl | Bash](https://www.sysdig.com/blog/friends-dont-let-friends-curl-bash), [разбор рисков на lesinskis.com](https://www.lesinskis.com/dont-pipe-curl-into-bash.html), [обсуждение на Kicksecure Wiki](https://www.kicksecure.com/wiki/Dev/curl_bash_pipe). Причины конкретно: скачивание и выполнение — не атомарная операция (обрыв соединения может исполнить частично загруженный/повреждённый скрипт), сервер может отдать разное содержимое в зависимости от того, определил ли он, что вызов идёт именно через `| bash` (invisible to a human eye), нет момента для проверки содержимого перед исполнением.

**Следствие для этого ТЗ**: провижининг **не** должен предлагать оператору команду вида `curl https://.../install.sh | bash`. Единственный поддерживаемый путь — клонирование репозитория (по зафиксированному тегу/коммиту, не "последняя версия ветки") и запуск Ansible **с control-машины** через SSH — сама модель Ansible (push через SSH с уже аутентифицированной машины оператора) структурно исключает этот антипаттерн, т.к. ничего не скачивается и не исполняется на целевой VDS вслепую.

### 2.3. Версионирование и ревью

- Playbook'и — под git, изменения — через pull request/код-ревью, как и любой другой код проекта (не "у меня на диске есть скрипт").
- Ansible Molecule (стандартный инструмент тестирования ролей Ansible) — для проверки idempotency роли перед применением к реальной VDS, если объём ролей вырастет настолько, что ручной проверки станет недостаточно.

## 3. Требование №5 пользователя (часть про VDS): закрытие дыр, только нужные порты, SSH в безопасном режиме

### 3.1. SSH — конкретные меры со ссылками

По [Mozilla OpenSSH Security Guidelines](https://infosec.mozilla.org/guidelines/openssh) и практике CIS Benchmark ([CIS Ubuntu Linux 20.04 LTS Benchmark](https://edu.anarcho-copy.org/GNU%20Linux%20-%20Unix-Like/Debian/CIS_Ubuntu_Linux_20.04_LTS_Benchmark_v1.1.0.pdf), сводка практик — [7 CIS Security Best Practices for Linux Servers](https://medium.com/@bornaly/7-cis-security-best-practices-i-apply-on-every-linux-server-i-set-up-8a8e723a4281)):

- `PermitRootLogin no` — прямой root-доступ по SSH отключён, работа только через sudo-пользователя (принцип наименьших привилегий).
- `PasswordAuthentication no` — только аутентификация по ключу.
- `MaxAuthTries 3` — ограничение попыток на соединение.
- Опционально — `AllowGroups`/`AllowUsers` для явного ограничения круга допущенных учётных записей.
- Шифры — по актуальному списку Mozilla: приоритет AEAD-алгоритмам (`chacha20-poly1305@openssh.com`, `aes256-gcm@openssh.com`, `aes128-gcm@openssh.com`), CTR-шифры — только для обратной совместимости.
- Создание отдельного непривилегированного пользователя с sudo для повседневной работы — стандартный первый шаг любого guide по начальной настройке сервера (см. [DigitalOcean: Initial Server Setup with Ubuntu 20.04](https://www.digitalocean.com/community/tutorials/initial-server-setup-with-ubuntu-20-04) — создание пользователя, копирование SSH-ключа, только потом отключение root/паролей).

### 3.2. Firewall — только нужные порты

- [ufw](https://www.digitalocean.com/community/tutorials/how-to-set-up-a-firewall-with-ufw-on-ubuntu) — рекомендуемый для Ubuntu инструмент поверх iptables/nftables; политика по умолчанию — **deny incoming**, явные allow-правила только для: SSH-порта, портов активных пресетов Hop A (на входных нодах), порта(ов) backhaul Hop B (на обеих сторонах — см. ТЗ-4 §6), порта mTLS-канала Agent↔Platform.
- Никаких портов "на всякий случай" — если порт не используется конкретной ролью ноды (входная/выходная), он не открывается вообще, роль явно определяет список правил (не единый профиль на все ноды без разбора).

### 3.3. fail2ban — дополнительный слой поверх ufw

По [DigitalOcean: Protect SSH with Fail2ban on Ubuntu](https://www.digitalocean.com/community/tutorials/how-to-protect-ssh-with-fail2ban-on-ubuntu-22-04): fail2ban работает на уровне приложения (парсит логи, банит IP по паттерну неудачных попыток), ufw — на уровне сети (порты) — это дополняющие, а не взаимозаменяющие меры, применяются вместе.

### 3.4. Прочее базовое хардненинг (стандартная практика, не специфика этого проекта)

- Автоматические security-обновления (`unattended-upgrades` на Debian/Ubuntu).
- Отключение неиспользуемых системных сервисов.
- Синхронизация времени (`chrony`/`systemd-timesyncd`) — важно для корректности TLS-сертификатов и логов с временными метками.
- Docker устанавливается из официального репозитория Docker (не из дистрибутивного пакета с устаревшей версией), demon сокет не публикуется наружу без крайней необходимости.

## 4. Функциональные требования к процедуре provisioning

1. **Базовая подготовка** (общая для РФ и зарубежных VDS): создание непривилегированного пользователя, настройка SSH (§3.1), настройка ufw+fail2ban (§3.2–3.3), установка Docker, базовое хардненинг (§3.4).
2. **Роль-специфичная подготовка**: открытие ролевого набора портов (входная нода — порты пресетов Hop A + backhaul; выходная нода — порт backhaul), передаётся как параметр playbook'а (роль ноды), не отдельный скрипт на каждый случай.
3. **Установка и enrollment Agent'а**: разворачивание Docker-контейнера Agent'а, передача адреса Platform и одноразового enrollment-токена (см. ТЗ-4, §5.2) — токен передаётся через Ansible Vault/SOPS-зашифрованную переменную, не открытым текстом в команде/истории шелла.
4. **Проверка результата**: playbook завершается верифицируемой проверкой — Agent появился в реестре Platform со статусом `HEALTHY` (см. критерии приёмки ТЗ-5) — если нет, оператор должен получить понятную диагностику, а не "playbook завершился с кодом 0, но ничего не работает".

Специфика РФ-нод: перед запуском provisioning для РФ-VDS остаются в силе критерии и AUP-разбор из [TZ-1-rossiyskiy-vds.md](TZ-1-rossiyskiy-vds.md) — этот документ их не заменяет и не дублирует, только предполагает, что выбор уже сделан.

## 5. Требования к безопасности (сводно)

- Все секреты (SSH-ключи, enrollment-токены, пароли) — только через Ansible Vault/SOPS, никогда в открытом виде в репозитории, командной строке (видна в истории/`ps`) или логах.
- Никакого `curl | bash` — только git + Ansible push по SSH с уже доверенной control-машины (см. §2.2).
- Ролевая модель портов (§3.2) — явный список на роль, не "открыть всё, разберёмся потом".
- SSH-хардненинг применяется **до** какой-либо иной настройки, включая установку Docker/Agent — минимизация окна незащищённого доступа к свежей VDS.
- Playbook'и проходят код-ревью перед применением к реальной production-ноде (§2.3).

---

## 6. Требования к удобству эксплуатации

- Ввод новой ноды в пул — одна команда (`ansible-playbook site.yml -l <новый-хост> -e role=entry|exit`), не последовательность из десятка ручных шагов.
- Идемпотентность — повторный запуск playbook'а на уже подготовленной ноде не ломает и не дублирует настройки (стандартное свойство Ansible-модулей при правильном использовании).
- Явная диагностика на каждом крупном шаге (SSH настроен → firewall настроен → Docker установлен → Agent зарегистрирован) — оператор видит, на каком шаге остановка, если что-то пошло не так.

---

## 7. Критерии приёмки

- [ ] Секреты provisioning (SSH-ключи, enrollment-токены) нигде не хранятся в открытом виде в репозитории — проверяется поиском по истории git и содержимому.
- [ ] После применения playbook'а: `PermitRootLogin no`, `PasswordAuthentication no` — проверяется фактическим SSH-подключением с паролем/под root (должно быть отклонено).
- [ ] ufw активен, разрешены только порты, соответствующие роли ноды — проверяется `ufw status` и внешним сканом портов.
- [ ] fail2ban активен и банит IP при серии неудачных SSH-попыток — проверяется имитацией неудачных попыток.
- [ ] Повторный запуск playbook'а на уже подготовленной ноде не изменяет состояние (идемпотентность) — проверяется через `--check`/сравнение до-после.
- [ ] После полного цикла provisioning + установка Agent нода появляется в реестре Platform со статусом `HEALTHY` без ручного вмешательства сверх запуска одной команды.
- [ ] Ни один из playbook'ов не использует паттерн "скачать скрипт и сразу исполнить" без предварительной фиксации версии/проверки содержимого.
