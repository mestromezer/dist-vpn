# ТЗ-3. Архитектура распределённой системы управления флотом нод (высокоуровневая фиксация)

> Статус: черновик для согласования — этот документ фиксирует высокоуровневые решения перед тем, как переходить к детальным ТЗ на каждую программу.
> Расположение: `C:\access\` — рабочая директория проекта (перенесено с `D:\access\` из-за сбоя диска `D:`, который на момент переноса не принимал запись целиком, не только папка `access`).

## 0. Что изменилось и что остаётся в силе

Технически реализованная ранее часть (`M1-deploy/`: конкретные конфиги Xray для фиксированной пары ru-entry↔foreign-exit, bash-оркестратор M5/M6) физически утрачена из-за сбоя диска. Но это не потеря знаний — вся конкретика есть в истории этого диалога, и, что важнее, **сам факт смены цели делает ту реализацию устаревшей независимо от утраты файлов**: она была рассчитана на ровно два зафиксированных в файлах узла, а не на управляемый пул узлов произвольного размера.

Что переносится в новую систему как **проверенные факты и решения**, а не как файлы для копирования:

| Что | Откуда | Статус в новой системе |
|---|---|---|
| Критерии выбора РФ-VDS (юрисдикция, ASN, AUP-пороги, red flags) | ТЗ-1 (`TZ-1-rossiyskiy-vds.md`, на диске цел) | Остаётся входным чек-листом при добавлении новой ноды в пул |
| VLESS+REALITY, схема полей (`realitySettings`, `network:"raw"/"xhttp"/"grpc"`, `password`=бывший `publicKey` и т.д.) | ТЗ-2 + переписка (M1–M3) | Домейн-логика, которую реализует **Agent** при конфигурировании своей Xray-ноды |
| Цепочка Hop A (клиент↔вход) → Hop B (вход↔выход) через chained outbound | ТЗ-2, M1 | Логика сборки каскада — теперь принимается **Platform**, применяется **Agent**'ами |
| Нативный failover `balancer`+`observatory`+`fallbackTag` | M2 | Остаётся: внутри одного каскада между несколькими exit-нодами это по-прежнему работает без всякого внешнего кода — Platform лишь формирует список кандидатов |
| Библиотека пресетов P1–P4 (RAW+Vision / XHTTP / gRPC / WS+TLS) | M3 | Остаётся как набор шаблонов конфигурации, которые Agent умеет поднимать по команде |
| Точный синтаксис `xray api adi/ado/rmi/rmo/adrules/rmrules/bo/bi/adu/rmu` (вычитан из исходников CLI) | M4–M6 | Прямо переиспользуется — это то, чем Agent будет управлять локальным Xray без рестарта |
| Приватная модель статистики (`policy.levels.statsUser*`, `metrics`/`/debug/vars`, `log.access:"none"`) | user-monitoring.md | Переносится как обязательное требование к Agent, данные агрегирует Platform |
| Идея "секрет пользователя (UUID) не меняется при ротации сервера" | M6 | Остаётся принципом ротации |
| Bash-оркестратор одной пары нод (`monitor.sh`, `rotate-hopa.sh` и т.д.) | M5–M6 | **Не переносится буквально** — заменяется Platform+Agent общего назначения (см. §7 про переиспользование готового ПО вместо самодельного bash) |

## 1. Цель системы

Управлять **пулом VDS-нод** (агентов), с ролями (входная/РФ, выходная/зарубеж, потенциально «универсальная»), автоматически собирать из них один или несколько каскадов Россия→зарубеж, с возможностью:

1. Добавлять/выводить ноды из пула через администратора, не трогая работающие каскады руками.
2. Автоматически перенаправлять пользователей на доступные узлы при обрыве конкретной ноды/канала — комбинация нативного failover Xray (внутри уже собранного каскада, как в M2) и активного переконфигурирования пула самой Platform (когда узел выбыл окончательно).
3. Централизованно управлять пользователями (добавление/удаление/учёт потребления) — без доступа к содержимому трафика (тот же принцип приватности, что уже был согласован).
4. Мониторинг здоровья нод и объёма потребления — общий для всего пула, а не на каждой ноде отдельно.

## 2. Три программных компонента

```
┌──────────────┐        mTLS/gRPC         ┌──────────────┐
│    Agent     │◀────────────────────────▶│   Platform   │◀────── Admin Client (Web UI / CLI)
│ (на каждой   │   регистрация, команды,   │ (центральный │        администратор
│  VDS-ноде)   │   телеметрия, heartbeat   │   сервер)    │
└──────┬───────┘                           └──────┬───────┘
       │ управляет локально                       │ хранит: реестр нод, реестр
       ▼                                           │ пользователей, топологию каскадов,
┌──────────────┐                                   │ историю ротаций, метрики
│  Xray-core   │                                   ▼
│ (в Docker,   │                           ┌──────────────┐
│  как раньше) │                           │      БД      │
└──────────────┘                           └──────────────┘
```

### 2.1. Agent

Ставится на каждую VDS (РФ-входную или зарубежную-выходную — роль назначает Platform, не хардкод). Обязанности:

- Поднимает и держит локальный Xray-core в Docker (тот же образ и паттерн, что уже отработан: `ghcr.io/xtls/xray-core`, монтирование `config.json`, `-c`/`-confdir`).
- Исполняет команды от Platform: добавить/убрать inbound/outbound/пользователя/правило маршрутизации/балансировщик — через `xray api adi/ado/rmi/rmo/adu/rmu/adrules/rmrules/bo` (без рестарта — то же самое, что уже подтверждено в M5/M6).
- Умеет поднять любой из пресетов P1–P4 по команде Platform (шаблоны конфигурации — то, что раньше было в M3, теперь — часть Agent'а, параметризуемая).
- Ротирует локальные секреты (REALITY-ключи, TLS-сертификат) по команде или расписанию, полученному от Platform — логика та же, что в M6 (двухфазно для клиентских пресетов, авто-хотрелоуд для TLS-сертификата P4), но теперь общая для любой ноды, а не bash-скрипт под конкретные два узла.
- Отдаёт телеметрию: health/heartbeat, байтовые счётчики (per-user/per-inbound/per-outbound — тот же принцип приватности), состояние наблюдателя (`observatory`/`balancer` info).
- НЕ хранит долгосрочное состояние сам — источник истины всегда Platform (agent может быть пересоздан/переустановлен без потери данных о пользователях/каскаде).

### 2.2. Platform (сервер)

Центральная точка управления:

- **Реестр нод**: список агентов, их роль, регион/юрисдикция, статус здоровья, версии.
- **Реестр пользователей**: централизованный (а не per-node файл, как было в user-monitoring.md) — один пользователь может быть привязан к нескольким каскадам/пресетам.
- **Топология/сборка каскадов**: какие входные ноды с какими выходными связаны (пул кандидатов на Hop B, как в M2, но теперь конфигурируется через UI/API, а не руками в `policy.json`).
- **Failover/эластичность**: реагирует на потерю heartbeat от ноды — краткосрочно ничего делать не обязательно (нативный `balancer`+`observatory` уже переживает временную недоступность одного exit'а), но при длительной недоступности/явном выводе ноды из пула — переконфигурирует оставшиеся каскады, при добавлении новой ноды — включает её в подходящие каскады.
- **Мониторинг**: агрегирует телеметрию со всех агентов, отдаёт Admin Client.
- **API** для Admin Client (REST/GraphQL — конкретика в детальном ТЗ).

### 2.3. Admin Client

Интерфейс администратора поверх API Platform:

- CRUD нод (добавить VDS в пул, назначить роль, вывести из эксплуатации).
- CRUD пользователей (добавить человека, отозвать доступ, посмотреть его потребление).
- Просмотр состояния каскадов/здоровья нод/алертов.
- Запуск ротации секретов (вручную или по расписанию).
- Минимально — CLI (для скриптуемости и для себя как единственного администратора на старте); Web UI — по необходимости, не обязателен для первой версии.

## 3. Топология и каскад — как это ложится на уже проверенную схему

Каскад — это по-прежнему `клиент → входная нода (Hop A, один из пресетов P1-P4) → выходная нода (Hop B, chained outbound + нативный balancer/observatory среди нескольких кандидатов)`. Меняется то, что раньше пул кандидатов Hop B был жёстко прописан в `ru-entry/config.json` (`to-foreign-exit-1`, `to-foreign-exit-2`, ...), а теперь:

- Platform хранит связь "входная нода X → [список выходных нод-кандидатов]" как данные, а не как конфиг-файл.
- При изменении этого списка (добавили новую выходную ноду, вывели старую) Platform отправляет Agent'у входной ноды команду `ado`/`rmo` (плюс, при необходимости, обновление `balancers[].selector`, для чего потребуется либо `adrules` с заменой правила, либо — что нужно уточнить в детальном ТЗ — работает ли префиксный `selector` балансировщика так, что новый outbound с правильным префиксом тега подхватывается автоматически без трогания самого правила балансировщика, как это уже было замечено при ротации в M6).
- Один вход может быть привязан к нескольким выходам (уже умели) и потенциально **несколько разных входов** — к разным (или пересекающимся) наборам выходов, если понадобится не один каскад, а несколько параллельных.

Открытый вопрос для детального ТЗ: нужна ли поддержка **многозвенных** каскадов (вход → промежуточный узел → выход, более 2 хопов) сразу, или пока хватает двухзвенной модели с возможностью растить пул выходов — по умолчанию предлагается закладываться на двухзвенную модель как основную, с расширяемой архитектурой на будущее.

## 4. Коммуникация Agent ↔ Platform

Раньше (M4) для связи между двумя конкретными нодами был собран самодельный туннель на VLESS+REALITY+Tunnel+Freedom — это было оправдано именно тем, что технология использования не поощерялась ("не искать готовые решения") и нод было ровно две. Теперь задача прямо противоположная: **явно приоритизировать готовые библиотеки/практики** для быстрой production-ready разработки. Поэтому control-plane канал Agent↔Platform предлагается строить на стандартном, широко задокументированном подходе, а не переизобретать:

- **gRPC + mTLS** (взаимная аутентификация сертификатами) — стандартная, давно устоявшаяся практика для управления флотом агентов (то же самое, на чём построены Nomad/Consul/большинство fleet-management систем); готовые библиотеки есть под любой стек.
- Открытый вопрос для детального ТЗ: должен ли этот канал сам маскироваться (например, идти поверх REALITY-фронта), учитывая, что сами ноды — те же VDS под потенциальным вниманием ТСПУ, или обычного mTLS на нестандартном порту достаточно, т.к. объём и характер control-plane трафика (редкие, короткие RPC) сам по себе не похож на то, что обычно фильтруют. Предварительная рекомендация: не усложнять на старте, mTLS gRPC на выделенном порту; вернуться к маскировке отдельной итерацией, если станет проблемой на практике.

## 5. Мониторинг и приватность (переносится как обязательное требование)

Без изменений по существу относительно уже согласованной модели:

- Только байтовые счётчики (uplink/downlink) per-user/per-inbound/per-outbound — никогда не адреса назначения и не содержимое.
- `log.access: "none"`, `dnsLog: false` — обязательное требование к любому конфигу, который Agent поднимает.
- Agent передаёt эти счётчики Platform (через тот же control-канал), Platform агрегирует и отдаёт в Admin Client.
- Технический источник данных на ноде — тот же (`policy.levels.statsUser*` + `metrics`/`/debug/vars`), меняется только то, что раньше сбором занимался bash-скрипт на конкретной ноде, а теперь — Agent, отправляющий их Platform.

---

## 6. Управление пользователями (переносится, централизуется)

- Один пользователь = одна запись в реестре Platform (не разбросанные по нодам `users.json`, как было).
- Добавление пользователя = Platform определяет, к какому каскаду/пресетам он должен иметь доступ, и рассылает соответствующим Agent'ам команду `adu` (тот же примитив, что уже проверен).
- UUID пользователя не меняется при ротации серверных секретов — принцип из M6 остаётся.
- Отзыв доступа = `rmu` на всех затронутых нодах через Platform.

## 7. Референсы: что уже существует на GitHub и почему не форкаем целиком

Проверено (актуально на дату написания):

- **Gozargah/Marzban** + **Marzban-node** — популярная (много звёзд, активна) панель управления Xray с моделью "панель + нода", REST API, управление пользователями/трафиком.
- **marzneshin/marzneshin** + **marzneshin/marznode** — форк Marzban, специально нацеленный на масштабируемость (несколько нод), Python-стек (панель: Python-бэкенд + TypeScript-фронтенд; marznode: Python 3.12+), REST API, CLI, мониторинг трафика/нод/пользователей. Лицензия — **AGPL-3.0**.
- **MHSanaei/3x-ui**, **Hiddify** — похожие панели, у 3x-ui тоже заявлена поддержка "multi-node".

Это очень близкий прецедент почти ровно того, что описано в §2 (Agent = marznode, Platform = marzneshin). Тем не менее форк целиком не рекомендуется как основа "как есть", по двум причинам:

1. **Модель топологии не совпадает.** У Marzneshin "несколько нод" — это про масштабирование/географию (пользователь подключается к любой из нод напрямую), а не про принудительное **каскадирование** конкретно ради того, чтобы обойти пограничный ТСПУ (клиент физически никогда не выходит из-под входной РФ-ноды напрямую в интернет, весь путь идёт через выходную ноду). Эта cascade-логика — ядро ценности всего проекта, и её придётся реализовывать в любом случае, поверх любой основы.
2. **Лицензия AGPL-3.0** — копилефт, распространяющийся в том числе на использование как сетевого сервиса. Для личного/небольшого закрытого использования это практически не создаёт проблем (некому предъявлять требование раскрыть исходники), но это стоит держать в уме как осознанный выбор, а не незамеченную деталь, особенно если система в будущем выйдет за рамки использования одним человеком/маленькой доверенной группой.

**Рекомендация для детальных ТЗ**: не форкать Marzneshin/marznode целиком, но:
- изучить их API/CLI как референс UX (что именно у них называется "нода", как устроено добавление пользователя и т.п. — не изобретать велосипед в мелочах);
- явно прописать в ТЗ на Agent/Platform приоритет использования зрелых библиотек для типовых задач (веб-фреймворк и ORM для Platform, gRPC-стек для Agent↔Platform, готовый Docker SDK для управления контейнером Xray — именно так, как это уже делалось в M5/M6 через `docker run`/Docker socket, только не самописным bash, а из кода Agent'а);
- не тратить время на переизобретение того, что уже есть в широко используемых открытых библиотеках (парсинг JSON-конфигов Xray, работа с Docker API, gRPC/mTLS boilerplate, ORM/миграции для БД Platform).
